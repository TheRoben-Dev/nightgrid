# Decisions

Non-blocking choices made during development. Newest last. Anything here can be revisited; open an issue or say so in the project thread.

## M0

### D-001 · `rusqlite` + `rusqlite_migration` over `sqlx`
Synchronous, zero-runtime, bundled SQLite (no system lib on any OS, works in Flatpak). `sqlx`'s compile-time checks need a DB at build time and pull in async machinery we don't need for a local file. `rusqlite_migration` tracks the version in `PRAGMA user_version`. `rusqlite` is pinned to 0.41 because `rusqlite_migration` 2.7 hasn't moved to 0.42 yet.

### D-002 · `keyring` v4 with its default (`v1`) API
v4 split into `keyring-core` + per-platform store crates; the umbrella crate's default feature keeps the familiar `Entry` API and enables the macOS Keychain, Windows Credential Manager and the zbus Secret Service store (pure Rust, no libdbus at runtime). Wrapped in our own `SecretStore` trait so we can swap to `keyring-core` + explicit stores later (e.g. a Flatpak-specific choice) without touching callers.

### D-003 · tauri-specta is a release candidate
`tauri-specta 2.0.0-rc.29` / `specta 2.0.0-rc.28` are the only maintained way to generate typed Tauri v2 bindings and the spec asks for them. They're pinned with `=` as upstream recommends. Risk: API churn between RCs; mitigation is that bindings are generated and checked in CI, so a bump either compiles and regenerates cleanly or fails loudly. Fallback if it stalls: `ts-rs` for types + hand-written invoke wrappers.

### D-004 · App identifier `dev.nightgrid.Nightgrid`
Reverse-DNS that's valid for Tauri (letters/digits/hyphens/dots), Flatpak app IDs and macOS bundle IDs, and doesn't end in `.app` (which Tauri warns about on macOS). It sets data/log dir names and the keychain service name, so changing it later means a migration. Rename alongside any product rename.

### D-005 · Toolchain versions
Tauri **2.x** (3.0 is alpha; spec pins 2). Vite 8, Svelte 5, vitest 5, ESLint 10 (flat config), TypeScript **5.9** (not 7: `typescript-eslint` and `svelte-check` don't support TS 7 yet). pnpm 10 pinned via `packageManager`.

### D-006 · Frontend tooling at the repo root, sources in `ui/`
`package.json`, `vite.config.ts`, `tsconfig.json` and the ESLint config sit at the root so `pnpm tauri ...` works from the root; Vite's `root` is `ui/` and it builds to `dist/`.

### D-007 · Visual direction from Roben's references
Sharp 1px hairline rectangles are the default container; chamfers only on primary buttons and the palette. **Magenta** marks selected/active (rail item, theme tile, current breadcrumb segment, slider thumb) with a soft glow; **mint** marks completed/neutral (past breadcrumb segments, checked boxes, filled slider segments); **yellow accent** stays for primary actions and keyboard focus as the spec says. Segmented stepper breadcrumb, 10-tick-style segmented sliders with `N/M` readouts, tile-grid selection cards, decorative barcode strips and hex IDs. All original; no assets or copy from the reference.

### D-008 · All four themes shipped in M0
They're only token sets, so ICE, BLOODLINE and PLAIN DARK ship now (spec lists them for M9). The terminal palette and iTerm2/Windows Terminal scheme import still come later.

### D-009 · UI scale stored as an integer percent
`uiScale: u16` (90–150) instead of a float avoids NaN/precision edge cases and types cleanly to TS.

### D-010 · Strict CSP without `'unsafe-inline'`
Svelte components avoid static `style=""` attributes (use `style:` directives), so `style-src 'self'` holds. Verified with a headless run under the same CSP: no violations.

### D-011 · Keychain integration test is opt-in
CI runners often lack an unlocked keychain/Secret Service, so the real-keychain round trip runs only with `NIGHTGRID_TEST_KEYRING=1`. The in-memory store covers the trait contract in CI.

### D-012 · Tray icon deferred to M7
The spec lists the tray as P0 but schedules it in M7 with notifications. M0 ships no tray to keep the capability set minimal.

### D-013 · Runtime `<style>` elements mirrored into constructable stylesheets
xterm.js injects `<style>` elements, which a CSP without `'unsafe-inline'` blocks (Chromium and WebKit check CSP for any `<style>`, whatever its `type`). Instead of loosening the CSP, `ui/src/lib/term/cspStyles.ts` makes `document.createElement("style")` return an inert `<nightgrid-style>` element and mirrors its text into `document.adoptedStyleSheets`, which CSP allows. Verified in Chromium and WebKitGTK with zero violations. Needs Safari 16.4+ / WebKitGTK 2.38+ for constructable stylesheets (macOS 11+ has it through Safari updates). Libraries that read `HTMLStyleElement.sheet` would not work with this.

### D-014 · Keep `freezePrototype`, rewrite xterm's prototype-shadowing assignments
With `Object.prototype` frozen, strict-mode code like `ns.toString = fn` throws, and xterm.js does exactly that at module load (bundled VS Code helpers), leaving a blank window. Rather than turn the hardening off, a small Vite plugin (`ui/tools/freezeSafe.ts`) rewrites such assignments in `@xterm/*` to `Object.defineProperty`. A test runs the rewrite over the installed xterm packages so an upgrade that changes the pattern fails CI instead of shipping a blank window.

### D-015 · Terminal keyboard rule
Shells need `Ctrl+K`, `Ctrl+B`, `Ctrl+W` and friends. On Windows/Linux, while a terminal has focus, the app only takes chords with Shift (plus `Ctrl+Tab`); the palette has a `Mod+Shift+K` alternative. On macOS, Cmd chords always go to the app since shells never see Cmd. Copy/paste on Windows/Linux is `Ctrl+Shift+C/V`.

### D-016 · Secrets entered at a prompt are cached in memory for the session
So reconnects and new panes don't re-prompt. The cache is per process, keyed by hop label, zeroized on drop, and cleared for a host when its connection settings change, it is deleted, or "remember" is turned off. Only an explicit "remember" writes to the OS keychain.

### D-017 · NIGHTGRID keeps its own `known_hosts`
New and accepted keys go to `<app_data_dir>/known_hosts`; `~/.ssh/known_hosts` is only read (as a fallback source) or copied on request, in line with "never write to the user's SSH config without asking". A key changed in either file blocks the connection.

### D-018 · Reachability is a TCP connect to the SSH port
ICMP needs privileges on most OSes. A TCP connect to port 22 (or the host's port) every 30 s while the window is visible gives online/offline plus latency without authenticating. Hosts behind a ProxyJump show "unknown" unless already connected.

### D-019 · SSH integration tests use an in-process server plus a real `sshd`
Docker isn't available on macOS/Windows runners, so the default suite runs an in-process russh server on every OS, and `core/tests/ssh_openssh.rs` starts a real OpenSSH `sshd` as the current user on Linux and macOS CI (`NIGHTGRID_TEST_OPENSSH=1`) to catch interop issues.

### D-020 · SFTP via russh-sftp on the pooled connection
`russh-sftp` speaks SFTP over any channel stream, so each host gets one `sftp` subsystem channel on its existing pooled connection (cached per connection; a reconnect opens a new one). Transfers between two hosts stream through the app rather than needing host-to-host SSH trust.

### D-021 · Atomic save uses `mv -f` over SSH for the final rename
SFTP v3 `RENAME` refuses to replace an existing file on OpenSSH, and russh-sftp has no `posix-rename@openssh.com`. The editor writes `.<name>.nightgrid-<id>.tmp` with the original's mode (and owner, via `setstat`), then runs `mv -f -- '<tmp>' '<file>'` on the same connection (one `rename(2)`, paths shell-quoted). Plain SFTP rename is tried first for servers that allow it. If the temp file can't be created (folder not writable) or the owner can't be kept, it falls back to rewriting the file in place, which keeps owner and mode but isn't atomic; the UI reports which happened.

### D-022 · Save conflicts are detected by size + mtime
The editor remembers the file's size and mtime when it opens (or last saved) the file and refuses to save over a file whose stamp changed. mtime has one-second resolution over SFTP v3, so two edits within the same second with the same size can slip through; that's an accepted trade-off against hashing every file before save.

### D-023 · Transfer conflicts are decided per top-level item
A job is one selected file or folder. If the destination exists, the job waits for "overwrite / skip / keep both" (or follows "apply to all"). Overwriting a folder merges into it and replaces files inside. Resume and retry skip the check and continue each file from the size already at the destination, so a retried job never asks twice.

### D-024 · CodeMirror is code-split
The editor and its language packs load on first use, keeping the main bundle under the 900 kB warning limit. CodeMirror injects its styles through constructable stylesheets, which our CSP allows, and none of its packages assign over `Object.prototype` members (checked against `freezePrototype` in a Chromium run).


### D-025 · Docker API over per-request SSH channels
bollard's custom transport hands us each HTTP request. We open a fresh `direct-streamlocal` channel to the daemon socket on the host's pooled SSH connection, run HTTP/1.1 over it with hyper, and let the channel close when the response body is done. That keeps the client stateless across reconnects (the per-host `DockerCache` is keyed to the pooled connection) and lets long log streams run beside short calls. Stats requests run 6 at a time so a big host doesn't use up sshd's session limit.

### D-026 · Socket discovery and dial-stdio fallback
On first use a small `sh` probe looks for a readable+writable socket at `/var/run/docker.sock`, then `$XDG_RUNTIME_DIR/docker.sock` (rootless), and checks whether the `docker` CLI exists. If the socket is there but not accessible, we stop with a "join the docker group" message instead of trying sudo. Being in that group is root-equivalent, and the UI says so. If forwarding fails (`AllowStreamLocalForwarding no`), we use `docker system dial-stdio` over an exec channel. With no socket but a CLI (contexts, a `DOCKER_HOST` in the login environment), dial-stdio is tried directly.

### D-027 · Container shell uses the docker CLI in a PTY
Exec over the API needs a hijacked HTTP connection plus our own TTY resize plumbing. Running `docker exec -it <id> sh -c 'command -v bash … || exec sh'` in a PTY channel reuses the terminal stack (resize, reconnect, copy/paste) for free. It needs the docker CLI on the host, which every normal install has. Container ids/names are validated (`[A-Za-z0-9_.-]`, no leading `-`) and shell-quoted.

### D-028 · Typing the host name only for removing several containers
Rule 5 asks for a confirmation that names the targets, and for typed names on multi-host runs. Docker actions are single-host, so stop/restart/kill/remove always show the exact containers. Only removal of more than one container also needs the host name typed, because removal is the one action you can't undo by starting the container again. Start, pause and unpause run without asking.

### D-029 · Env values travel to the webview but are masked there
`docker_inspect` returns env values, so the panel can reveal them on click without another round trip. They are masked by default in the UI, replaced with `••••••` in the raw JSON view, and never logged (bollard's debug logging is filtered out). They are never written to SQLite.

### D-030 · "Edit in Nightgrid" is a session-only shell hook
Roben wanted normal editor keybinds instead of nano when editing on a server. With the setting on, SSH terminals start through a bootstrap: `echo <base64> | base64 -d | /bin/sh`. That form only uses base64 characters, so any login shell (sh, bash, zsh, fish, csh) runs it the same way. It creates a private `mktemp -d` folder holding an editor helper and starts the user's shell as a login shell: bash via `--rcfile`, which sources `/etc/profile` and the first of `~/.bash_profile`/`~/.bash_login`/`~/.profile`; zsh via a `ZDOTDIR` shim that sources the real dotfiles; fish via `-C`. It defines a `nano` function and sets `EDITOR`/`VISUAL` to the helper, and removes the folder when the shell exits (folders left over from a dropped connection are cleaned after a day). The helper prints `OSC 7766;<token>;<base64 abs path>` and waits with echo off until the app types the token back (tab closed) or the user presses Enter. The token is random per terminal start, so file contents that happen to contain the sequence don't open anything. The app opens files only on that same host, over SFTP as the SSH user. `sudo nano` still runs real nano; `sudoedit` works because it edits a user-owned temp copy. The hook is off by default because it changes how the remote shell starts (for example `logout` says "not a login shell" in bash), and it is never used for container shells.

### D-031 · Editor keybinds stay CodeMirror's standard keymap
The built-in editor already uses the platform-standard bindings: CodeMirror's default, history, search and fold keymaps (`Mod+Z`, `Mod+Shift+Z`/`Mod+Y`, `Mod+F`, `Mod+A`, Shift+arrows, Home/End), plus `Mod+S`. No vim/emacs modes and no nano-style chords.

### D-032 · Compose runs the CLI on the host, not the API
Compose is a client-side tool, so stacks run `docker compose` (or `docker-compose`) in the stack folder over an SSH exec channel, with `exec 2>&1` so progress and errors arrive in order. For rootless sockets we set `DOCKER_HOST` the same way as for dial-stdio. The project name, folder and compose files come from the container labels (or the folder scan), are checked (compose's project-name rule, absolute paths without control characters) and are shell-quoted. Cancel sends SIGINT on the channel, like Ctrl-C. "Update" compares each service's image id before the pull and after `up -d`, and lists only the services that changed.

### D-033 · Stack folders are per host, in SQLite
Running containers only reveal stacks that are up. To manage stacks that are down, the user adds folders per host (`stack_dirs` table, migration 0004). A short `sh` scan looks for compose files in each folder and one level below. Paths may start with `~`, which expands on the host. No secrets are involved; `.env` files stay on the host and are only read when the user opens one in the editor.

### D-034 · Which stack actions confirm
Down, Restart and Update interrupt running services, so they confirm with the stack name and host (rule 5). Up and Pull don't stop anything that is running and run straight away. Stack actions are single-host, so no typed name is needed.

### D-035 · ASCII host icons live in the existing `hosts.icon` column
Roben asked for an ASCII icon above each saved host's name, styled like the app. The `icon` column has existed since migration 0001 and was unused, so the art text is stored there directly (no migration, and it travels with the host). Presets are just text the editor fills in, so changing a preset later doesn't change hosts that already use it. The backend normalizes and validates the icon (≤ 8 lines × 32 characters; printable ASCII, Latin-1, arrows, box drawing, blocks, geometric shapes and braille, which are all single-width in monospace fonts; no control characters, so nothing can inject terminal or markup sequences). The UI applies the same rules to warn as you type. Icons render as plain text (white-space: pre), never as HTML.

## M4

### D-036 · Metrics come from one `sh` script per sample, nothing installed
Each sample runs one short POSIX `sh` script on an exec channel of the host's pooled SSH connection. It prints `/proc/stat`, `/proc/meminfo`, `/proc/loadavg`, uptime, `uname -sr`, the hostname, `/proc/net/dev`, `/proc/diskstats`, `/proc/mounts`, `df -kP` (wrapped in `timeout 4` where available, so a hung NFS mount can't stall it) and hwmon/thermal sensor readings, each after an `@@section` marker. Parsing happens in Rust (`core/src/metrics/parse.rs`) and is forgiving: a missing section only blanks that metric, so BusyBox, old kernels and containers work. Rates (CPU %, network, disk I/O) are computed in the app from consecutive raw snapshots, so the script keeps no state on the host. Virtual interfaces (veth, docker, bridges, CNI) and virtual block devices (loop, zram, dm, md) are left out of the totals; pseudo filesystems and Docker/snap overlay mounts are left out of the disk list. Linux only for now; other OSes show "no metrics".

### D-037 · History is minute points plus 15-minute rollups in SQLite
Samples are averaged per host into one point per minute (`metric_points`, res 60, migration 0005). Each minute point also updates a running average in a 15-minute row (res 900), so long ranges never scan minute data. Minute points are kept for **Settings → Monitoring → Keep detail** days (default 7, max 90) and rollups for at least 90 days; pruning runs hourly. Ranges up to 2 days read minute points, longer ones read rollups. Only numbers are stored: no hostnames, mount names or process data. History is recorded only while Nightgrid runs.

### D-038 · Polling follows what's on screen and never prompts
Every saved host gets a poller while metrics are on. Hosts shown on the Overview or in an open monitor are sampled at the fast interval (default 2 s); the rest at the background interval (default 60 s), which also applies when the window is hidden. Offline hosts back off from 5 s to 5 min, and Retry wakes them. A poller never shows a prompt: if a host needs a password, a passphrase or a host-key decision it goes to "login needed" and waits until a terminal or file pane has connected that host, then reuses the pooled connection. This keeps background work from surprising the user with dialogs and keeps security rules 2 and 3 in the user's hands.

### D-039 · Float fields are exported to TypeScript as `number`
specta exports `f32`/`f64` as `number | null` (because of NaN/Infinity). Metric structs never contain NaN (parsers drop non-finite values), so their float fields are annotated `specta(type = u32)` to get a plain `number` in `bindings.ts`. The annotation only changes the generated type; serde still writes the float.

### D-040 · App icon is a terminal window in the theme colours
Roben picked a terminal window with a title-bar stepper, drawn with the NIGHTGRID tokens in the roles the UI gives them: mint hairline frame, magenta for the active step and cursor, mint for the finished step, cyan for the prompt. The tile follows the macOS grid (an 824 px rounded square on a 1024 px canvas), so it sits right in the Dock next to other apps; Windows and Linux use the same art. `app/icons/source.svg` is the source of truth; regenerate the platform files with `pnpm tauri icon app/icons/source.png` (render the SVG to a 1024 px PNG first) and keep only the files `tauri.conf.json` lists.

### D-041 · Panel sizes live in localStorage, not settings
Roben wanted adjustable workspace borders. One `Resizer` component drives every splitter (pointer drag, arrow keys, Home/End, Enter/double-click to reset) against a small layout store with a min, max and default per size. Sizes are per-machine layout preferences, so they're kept in the webview's localStorage (`nightgrid.layout.v1`) rather than in SQLite settings. A laptop and a desktop can then keep different layouts, and nothing sensitive is involved. Split sizes are percentages of the parent, so they survive window resizes; the sidebar width is in pixels.

### D-042 · DRIFT is the LLM helper's mascot
Roben chose DRIFT, a 24×18 pixel HUD drone, from four original concepts and a round of variants. It is drawn only with theme tokens: a dark hull, a mint hairline outline, chamfered corners like the app icon, a forehead stepper, cyan eyes and a magenta thruster. That way it recolours with the theme and fits the UI instead of sitting on top of it. Pixel art was chosen because it stays crisp at integer scales and its states are cheap frame swaps that still work with reduce effects. The reference sheet, frame data and spec are in `docs/mascot/`, and `drift-sprites.json` is the source of truth for the implementation.

### D-043 · Self-update runs from Rust against GitHub "latest"
The Tauri updater plugin is used from Rust only (`update_check` / `update_install` commands); its JS commands are not granted to the webview, so the IPC allow-list stays small (rule 8). The endpoint is `releases/latest/download/latest.json` on the project's GitHub, which counts as "the update server" in rule 7. Because `latest` skips prereleases, releases are now published as regular releases. The CI release job writes `latest.json` from the signed bundles (`scripts/updater-manifest.mjs`), with this version's CHANGELOG section as the notes. The notes are shown as plain text. `requireSignedVersion` is on, so a manifest can't pair a new version number with an older signed bundle. The public key lives in `app/updater.pub`; while it's empty, checks return `notConfigured` and CI builds without updater artifacts, so nothing breaks before Roben generates the key. Linux updates only the AppImage; deb/rpm are left to the package manager. A launch check happens once, 8 s after start, and only when enabled. "Skip this version" is stored in settings.

### D-044 · The scramble effect is part of the identity, used widely
Roben asked for the glitch text animation in more places, so spec §4's "boot, first panel title, alerts only" rule is relaxed. The `scramble` action owns its element's text and re-decodes when the text changes. Duration scales with length (220–650 ms), so labels settle almost instantly. It is applied to view titles, panel and dialog titles, notices and error lines, and host state words. It is deliberately not applied to live numbers, logs, terminal output or file contents. It is fully off under reduce-effects, the plain theme and `prefers-reduced-motion`.

### D-045 · Service checks run from this computer, and capture the certificate even when it isn't trusted
A health check is one HTTP/1.1 GET from the app straight to the service URL (no agent, no SSH): status, time to response headers and, for https, the leaf certificate. TLS goes through rustls with the OS verifier (so internal CAs installed in the system store count as trusted), wrapped by a verifier that records the leaf and the verdict and then lets the handshake finish, so the board can say "self-signed, 40 days left" instead of only "down". Handshake signatures are still checked by the real verifier. An untrusted certificate marks the service down unless the user ticks "allow untrusted", which turns it into a warning. Redirects are not followed and 3xx is healthy by default (`200-399`, editable per service), because login redirects are the norm for self-hosted apps. Checks run every 60 s by default (15 s–15 min), 8 at a time; results are kept 30 days for the latency trend and 24 h uptime. Service icons from Homepage are stored but never fetched (no remote content in the webview, rule 8); cards show a monogram.

### D-046 · Homepage import is a re-runnable sync keyed on group/name
`services.yaml` is read over SFTP from a chosen host (or locally), parsed with yaml-rust2 (nested groups flattened to `Parent / Child`, `href` or else `siteMonitor` as the URL, entries with `{{HOMEPAGE_VAR_…}}` templates or no URL skipped and listed), and ordered by `settings.yaml`'s `layout:` when present. "Detect" looks for a container whose image name contains `homepage` and offers its `/app/config` mount, as a convenience only. Imported rows carry `source = homepage` and `source_key = "group/name"`, so running the import again updates name, URL, group, description and icon from the file while keeping what was set in Nightgrid (checks, healthy codes, untrusted toggle, host link). Entries gone from the file are reported and only deleted when "remove services no longer in the file" is ticked. Nothing is ever written back to Homepage.

### D-047 · Tunnels ride the pooled connection and reconnect until stopped
A running tunnel is one task: get the host's pooled SSH connection (`connect_host`, never prompting), serve, and when the connection drops, retry with backoff (2, 5, 10, 30, 60 s) until the user stops it, like autossh. Problems retrying can't fix (port in use, server refused the remote listen, host needs a login) stop it with the reason. Local and SOCKS listeners are bound before the tunnel reports "up", so a busy port fails immediately. Remote forwards are routed by bound port through a per-connection map that the russh handler consults for `forwarded-tcpip` channels; unknown ports are rejected, and dropping the forward cancels it on the server. SOCKS is SOCKS5 CONNECT without authentication, which is why listeners default to loopback (127.0.0.1 locally, `localhost` on the server); any other bind address shows a "reachable from other machines" warning in the editor and a PUBLIC chip in the list. Auto-start tunnels start when the app opens and again whenever their host gets a new connection. "Open through tunnel" (Tunnels toolbar and service cards linked to a host) creates an unsaved local forward on a free port, reuses it for the same target, and opens the rewritten `http(s)://127.0.0.1:<port>/…` URL in the system browser; an https service will show a certificate name mismatch there, which is expected. Traffic counters are byte totals through the local end, sent once a second while anything runs.

### D-048 · sudo: password on stdin, checked first, prompted per action
Root commands run as `sudo -S -k -p <marker> -- sh -c '<cmd>'` on an exec channel. The password is written to the channel as one line followed by EOF, so it never appears on a command line, in the environment, in `ps` or in a log; `-k` makes sudo always consume that line (a cached timestamp would otherwise pass it to the command's stdin), and EOF makes a wrong password fail at once instead of waiting for a second try. sudo's prompt marker and "Sorry, try again" are stripped from output, and its own failures are classified (needs password / wrong password / not in sudoers / sudo missing) so the UI can react. Before each privileged action one round trip checks `id -u` and `sudo -n true`: root and NOPASSWD hosts never see a prompt. Otherwise the password comes from the prompt for that action, or from the keychain only if "remember for this host" was ticked (off by default, rule 4); it is checked with `sudo true` before the real command starts, so a long upgrade never begins with a bad password, and a stored password that stopped working is deleted and the prompt shown again. Nothing is cached in memory between actions. Commands always go through `sh -c` so the user's login shell (fish, zsh) doesn't matter.

### D-049 · System view scope: services, JSON journal, three package managers, SMART heuristics
- **Units:** service units only (`list-units --all` merged with `list-unit-files`, so disabled services can be started or enabled; templates like `getty@.service` are left out). Stop, restart and disable confirm with the unit and host named; start, reload and enable don't, since they don't interrupt anything. Timers and the user manager are left for the backlog's timer explorer.
- **Journal:** `journalctl -o json` parsed per line (binary `MESSAGE` byte arrays are decoded lossily), streamed in batches, newest 5000 rows kept in memory, follow mode stopped with SIGTERM plus a channel close. When journalctl says only the user's own entries are visible, the view offers **Read with sudo** instead of failing.
- **Packages:** apt (`apt list --upgradable`, with a note when lists are over two days old and a sudo **Refresh lists**), dnf (`check-update`, handling dnf4's wrapped lines) and pacman (`checkupdates`, falling back to `pacman -Qu` with a note). Image-based systems (`/run/ostree-booted`) are detected and left to rpm-ostree/bootc. Reboot required = `/var/run/reboot-required` (with its package list), a running kernel whose modules are gone, or `needs-restarting -r`. Upgrades run non-interactively (apt keeps existing config files, `--with-new-pkgs` but no removals) and stream output; they are not detached from the SSH session, so the dialog warns to stay connected. Reboot needs the host name typed.
- **SMART:** one sudo session runs `smartctl --scan-open` and `smartctl -a -j` per device. Health is the worst of: self-assessment failed or an attribute at/below its threshold (FAILING); non-zero reallocated/pending/offline-uncorrectable/uncorrectable/CRC/spin-retry counts, NVMe media errors, ≥ 90 % endurance used or running hot (HDD > 55 °C, SSD > 65 °C, NVMe > 70 °C) (WARNING); unreadable devices such as unknown USB bridges (UNKNOWN). Each reason is listed in plain words on the disk's card.

## M7

### D-050 · Alerts are derived from existing watchers, with grace periods and a never-prompt rule
Alerts don't add a second monitoring system: one loop every 15 s reads the metrics pollers' states and latest mounts and the service checker's latest results, lists containers every 60 s and reads SMART every 6 h, and only on hosts already in the SSH pool (no background connections, no prompts; SMART runs only when `resolve_sudo` succeeds without input, i.e. root, NOPASSWD or a remembered password). Sources report conditions to a pure `Tracker` (`core/src/alerts.rs`) that owns grace periods (host offline 120 s, service down 90 s, the rest immediate) and a 5-minute clear hold for disks so a mount hovering at the threshold doesn't flap. Each report is scoped by source and, where a source only saw some hosts (Docker, SMART, disk usage of hosts currently sampled), by host, so a host that's offline keeps its other alerts instead of having them "resolve". Containers only alert after they were seen running in this session and then stop with a code other than 0/143 (or restart, or turn unhealthy), so containers kept stopped on purpose never alert. Active alerts and the last 200 resolved ones live in memory only; nothing about alerts is written to disk except the settings.

### D-051 · Delivery: native notifications, quiet hours, webhook URL in the keychain
New alerts become native notifications through `tauri-plugin-notification`, sent from Rust so the webview gets no notification permission. More than three in one round become one summary. Quiet hours (a local-time window that may wrap midnight) hold notifications and webhooks but alerts still show in the app. The optional webhook posts to ntfy (plain body with Title/Priority/Tags headers), Discord (`content` with mentions disabled) or a generic JSON endpoint (`{source, state, alert, headline}`); the URL is treated as a secret (Discord and ntfy URLs act as tokens) and kept only in the OS keychain, with just its scheme and host shown back. Webhook requests use a small shared HTTP client (`core/src/http.rs`, hyper + rustls with the OS verifier) that refuses untrusted certificates before anything is sent. This is a "configured integration" under rule 7: nothing is sent unless the user picks a webhook and saves a URL.

### D-052 · Tray menu is rebuilt only on change; close-to-tray is opt-in
Tauri's tray menus can't be patched in place across platforms, so the menu is rebuilt from a content signature (hosts and their poll state, saved tunnels and whether they run, alert counts) on each alerts round and right after a tunnel is toggled from it. Quick connect and "open alerts" are emitted as events to the UI, which opens a terminal through the normal flow (host-key and password prompts included); the tray never connects by itself. On macOS the icon is a template image so it follows the menu bar's light/dark style; elsewhere it's the app icon. Linux loads libayatana-appindicator at runtime, which panics when it's missing, so tray creation is wrapped and a missing library only logs a warning. "Keep running when the window is closed" defaults off so closing still quits as people expect; it only hides the window while a tray icon exists to bring it back.

### D-053 · Integrations are read on demand from this computer, with secrets in the keychain
Plex, AMP, Uptime Kuma and Portainer are stored as rows in an `integrations` table (kind, name, base URL, login name, status-page slug, Portainer endpoint, linked host, allow-untrusted), never with a token or password: those go to the OS keychain under `integration-<id>`, and the list only reports whether one is saved (rule 1, rule 6: masked in the editor with click to reveal). Status is read by the shared one-request HTTP client (`core/src/http.rs`) only while the Services view is open, every 30 s and paused when the window is hidden, so nothing polls in the background and the only calls go to URLs the user entered (rule 7). Each client parses into a small typed status: Plex `GET /` and `/status/sessions` with `X-Plex-Token`; Uptime Kuma's public status-page APIs (`/api/status-page/<slug>` and `/heartbeat/<slug>`), so no Kuma API key or socket.io login is needed; Portainer `GET /api/system/status` for reachability and version, used only to build "Open in Portainer" links for containers on the linked host (no Portainer token, nothing is managed through it); AMP logs in with `/API/Core/Login` for each read or action and drops the session id afterwards. AMP stop and restart are destructive (rule 5): the UI confirms with the instance named, instance names are validated before they reach a request, and the action is logged with its target; start runs at once. The kind of an integration can't change after it's created, so a stored secret never ends up sent to a different kind of server. Untrusted certificates are refused unless "allow untrusted" is ticked, as with service checks (D-045).

### D-054 · Snippets and playbooks: `{{variables}}` filled per run, values shell-quoted
Snippets are a command plus a scope (all hosts, one host, one group; it decides where the palette offers them, not where they may run) and a "run as root" flag. Playbooks are an ordered list of typed steps stored as JSON: command (optionally as root), upload a file from this computer over SFTP (with optional permissions), wait for a TCP port as the server sees it, and Docker start/stop/restart/pull. They stop at the first failed step unless that's turned off. Every text field may use `{{name}}` or `{{name=default}}`; `{{host}}`, `{{hostname}}` and `{{user}}` are filled per host. Values go into commands shell-quoted unless they only contain characters a shell treats literally, so a value can never start a second command; the cost is that placeholders must not be wrapped in quotes, which the editor says. Paths, hosts and container names are inserted as typed and validated where they're used (container and image references against a character allow-list). Unknown step types in stored JSON are skipped rather than failing the list, so an older build can open a newer database. Not Ansible on purpose (spec §8): no loops, conditions, facts or inventories.

### D-055 · Multi-host runs: pooled connections, 8 hosts at a time, never prompting
A run resolves to a plan (one command, a snippet or a playbook) and a host list. Hosts run in parallel, at most 8 at once, steps in order on each; output is streamed per host as stdout/stderr/info lines, batched up to 500 per message, and the UI keeps the last 5,000 lines per host. Connections come from the same pool as terminals and never prompt: a host that needs a login or an unknown host key fails with "needs a login" and a Connect button, then "Select failed" re-targets just those hosts. Root goes through the M6 sudo path (D-048) per host: root and NOPASSWD hosts need nothing, a remembered per-host password is used if there is one, otherwise the optional password typed for the run is sent on stdin to the hosts that ask and dropped when the run starts (it is never remembered from here). Stop sends SIGTERM to running commands and skips the remaining steps. "Wait for port" opens an SSH `direct-tcpip` channel to the target once a second, so nothing has to be installed on the host; a server with `AllowTcpForwarding no` fails at once with that reason.

### D-056 · Destructive runs are detected from the command text and confirmed with the targets
`automation::danger` splits a command into simple commands (on `;`, `|`, `&`, newlines, subshells), drops wrappers (`sudo`, `env`, `nohup`, `timeout`, `VAR=x`) and flags rm/shred/dd/mkfs and friends, kill/pkill/killall, reboot/shutdown/poweroff, `systemctl stop|restart|disable|mask`, Docker/Podman rm/rmi/kill/stop/restart/prune and `compose down`, package upgrades and removals (apt, dnf, yum, zypper, pacman, apk), `zfs destroy`, `find -delete`, `git reset --hard`/`clean`, and `>` redirects to anything outside `/dev` (spec rule 5's rm, prune, kill, down, reboot, shutdown, upgrade, overwrite). Playbook uploads count as overwrites of their remote path, and Docker stop/restart steps are flagged too. The check runs on the text as typed and as rendered, and it is deliberately cautious (it would rather ask too often). A destructive run shows a red dialog listing what was found and the hosts; on several hosts the user types the group's name (when exactly one whole group was picked) or the number of hosts. The backend logs every run with its hosts and, for destructive ones, what was found; output itself is never logged.

## M9

### D-057 · Config backups: one age-encrypted JSON bundle, never written in the clear
Export reads the config tables (groups, tags, hosts and their tags, bookmarks, stack folders, services, tunnels, integrations, snippets, playbooks, settings) row by row into a versioned JSON bundle and encrypts it with an age scrypt passphrase recipient (minimum 8 characters, work factor tuned by age to about a second), so any `age -d` can open it too. Metric points and service checks are history and stay behind. There is no unencrypted export at all, which keeps rule 1 simple: secrets can only ever be inside an encrypted file. Saved passwords, key passphrases, sudo passwords, integration tokens and the alert webhook are added only when "Include saved passwords and tokens" is ticked (off by default), read from the keychain and addressed by the exporting row's id; the plaintext buffer is zeroized after encryption. Files are written next to the target and renamed into place with mode 600, so a sync tool never picks up half a file. Rows are copied by column name, so an older backup loads into a newer schema (missing columns take their defaults) and unknown columns are ignored; a backup from a newer schema is refused. `age` is pinned to 0.11 because 0.12 pulls an `ml-kem` that can't share a lockfile with russh 0.65's.

### D-058 · Import merges by natural keys or replaces everything, in one transaction
**Merge** keeps what's here: each incoming row is matched by a natural key (group and tag by name, host by SSH alias or name + address + port, service by name + URL, tunnel by host + kind + bind address + port, integration by kind + URL + name, snippet and playbook by name, settings by key); matches are skipped and their old ids mapped onto the existing rows, new rows get fresh ids, and references (host → group, tunnel → host, snippet → group, ...) are rewritten through those maps. Merging the same file twice adds nothing. **Replace** deletes every config table (history goes with the hosts and services through cascades) and loads the rows with their ids; it's destructive, so it needs `replace` typed (rule 5). Either way it's one SQLite transaction: a bad row rolls the whole import back. Keychain entries are moved afterwards: a replace first deletes the entries of every host and integration that existed (otherwise a new host could inherit an old host's password through a reused id), then bundled secrets are saved for rows that were actually inserted; an existing row's secret is never overwritten by a merge. The sync folder is a path on this machine, so it's kept when imported settings replace ours. The app restarts after an import so every view, poller and tunnel reloads.

### D-059 · Files are picked with native dialogs in Rust; the sync folder is just a remembered path
`tauri-plugin-dialog` is used only from Rust (the save/open/folder pickers run inside the backup commands), so the webview gets no dialog or file-system permission and the capability file is unchanged; the file picked for import is remembered in app state between preview and import instead of being sent back from the UI. The optional sync folder (Syncthing, a cloud drive, a git repo) only saves the dialog: export writes and import reads `nightgrid-backup.age` there. The passphrase is never stored, so there is no automatic background backup; that would need the passphrase in the keychain and is left for later if it's wanted.

### D-060 · Handheld preset is a switch over existing settings; controller input is spatial focus navigation
"Handheld layout" sets `--hit` to 44 px (touch guidance is 44-48 px), widens button and field padding, and in the same update turns on the icon-only sidebar and raises UI scale to at least 130 %; those stay normal settings the user can change afterwards, and turning the preset off restores 100 % scale. Controllers use the webview's Gamepad API (standard mapping), polled with `requestAnimationFrame` only while a pad is connected, the window is visible and focused, and "Controller navigation" is on (default on, since it does nothing without a pad). The D-pad and left stick move DOM focus to the nearest focusable element in that direction (`pickNext`: distance along the axis plus double the sideways offset, so moving down stays in a column), limited to the topmost open dialog; A clicks the focused element, B cancels the open dialog or sends Escape, the bumpers cycle views, Start opens the palette. This reuses every existing button, keyboard handler and confirmation instead of adding a parallel "console UI", and it can't trigger anything a mouse click couldn't. Text fields and terminals keep left/right. No new permissions are involved.

### D-061 · Packaging stays at DMG, NSIS + portable zip, AppImage, .deb and .rpm
The spec lists Flatpak and an AUR package for M9. Nightgrid is a personal app that isn't being distributed, and the existing CI already produces an installer for every platform the user runs (macOS DMG, Windows NSIS + portable zip for the Ally, Linux AppImage/.deb/.rpm), with the in-app updater on top. A Flatpak would add a sandbox that needs portal work for SSH agents, `~/.ssh/config` and the keychain, and the AUR needs a maintained PKGBUILD; both are maintenance without a user. They are skipped; the AppImage covers Arch/CachyOS.


### D-062 · Updater signing key in place
Roben generated the minisign key pair. The public key is in `app/updater.pub` (base64, as Tauri expects) and, identically, in `tauri.conf.json` (the CLI signs against that copy; a test keeps them equal); the private key and its password are the `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` repo secrets and never leave GitHub. From 0.9.2 every release ships signed `.app.tar.gz` / `-setup.exe` / `.AppImage` bundles with `latest.json`. The release job now fails if the app carries a public key but no signed bundles were built, so a missing or broken secret can't silently ship a release that installed copies can't update to. 0.9.1 and older have no key and need a manual install of 0.9.2 once.

### D-063 · DRIFT's default model: Qwen3-4B-Instruct-2507, Q4_K_M
The spec asks for a 3–8B model that fits 6–8 GB of VRAM and runs on Apple Silicon. Qwen3-4B-Instruct-2507 at Q4_K_M is 2.5 GB on disk and about 3.5 GB in use with an 8k context, so it also fits 8 GB Macs. It is Apache-2.0 (Qwen2.5-3B's licence is research-only), it's the non-thinking instruct variant (no `<think>` blocks to hide), and it handles the short instructions this helper needs. The file is pinned to commit `a06e946` of `unsloth/Qwen3-4B-Instruct-2507-GGUF` with its SHA-256 and size; changing the model means changing `DEFAULT_MODEL`. The spec prefers mirroring it on Nightgrid's GitHub Releases, but release assets are capped at 2 GB, so the pinned Hugging Face URL (with the checksum) is used instead. Downloads resume and are only ever started by a click.

### D-064 · Helper architecture: llama.cpp in a separate crate, prompts and retrieval in the UI
llama.cpp is embedded through `llama-cpp-2` in its own crate (`llm/`), so the core crate's tests don't wait on a C++ build. macOS builds with Metal; Windows and Linux use the CPU for now (a 4B Q4 model gives a few tokens per second there). Vulkan/CUDA builds need SDKs on the CI runners and are left for later. The webview builds the prompt: it already knows the current view, host and selection, the `data-guide` targets live next to the markup they describe, and the user can see and remove context before asking. Retrieval is BM25 over the bundled user guide (instant, no embedding model, works offline), and M11's knowledge base will add articles to the same index. The model is told to answer Nightgrid questions only from the retrieved sections. Rust only runs the model, which keeps the IPC surface to seven small commands. "Show what will be sent" is met by context chips the user can remove before asking, plus a "What I was given" disclosure on every reply showing the exact prompt. Since the model is local, nothing is actually sent anywhere. Secret-looking values (`*_PASSWORD=`, tokens, URL credentials, private keys) are masked first anyway. Actions use a plain-text line format (`[[show docker]]`, `[[point hosts-add: …]]`) that small models follow reliably. The parser validates them against the known views and targets, and they only navigate and outline; they never click.

### D-065 · "Explain" hands DRIFT labelled text; nothing new crosses IPC
Each Explain button collects text the view already has in memory (log lines, journal entries, compose output, an automation host's command, steps and output, or the editor's buffer) and calls `helper.explain`, which sets it as the attached context with a source label ("Docker logs: web") and asks a fixed question. Selected lines inside that view win over the whole buffer, so the user can narrow it. The amounts are capped where the text is gathered (150 log/journal lines, 200 output lines, about 6,000 characters of a file from the top) so the 8k context keeps room for the guide and the answer; the prompt builder still cuts anything longer. The prompt says "Attached (source):" instead of "Selected text:" so the model knows what it's reading. No new commands or permissions: the text goes through the same path as a selection (masked, shown as a chip, listed under "What I was given"). If the model isn't ready, the question is left in the box instead of failing, and the buttons are hidden while the helper is off so the views stay unchanged for people who don't use it.

### D-066 · Scheduled jobs are read with one unprivileged script; cron times are computed in Rust
The Schedules tab runs one `sh` script: timer names from `list-units`/`list-unit-files`, then a single `systemctl show --timestamp=unix` for all of them (falling back to the human format on systemd older than 248, where next/last runs aren't parsed) and one more `show` for the started services' `Result`/`ExecMainStatus`; then `crontab -l`, `/etc/crontab`, readable `/etc/cron.d/*` and the `cron.<period>` folders, plus the host's `date +%s` and `+%z`. Nothing needs root, so it never prompts for sudo; other users' spool crontabs are left out and the tab says so. Cron schedules are parsed in Rust (lists, ranges, steps, month/day names, `@daily`-style macros, Vixie's day-of-month OR day-of-week rule) and the next run is found by walking days, then minutes, in the host's local time at its current UTC offset, so a run across a DST change can be an hour off. It's read-only on purpose: editing crontabs and timers is left to `crontab -e` and unit files in a terminal or the editor, which already have their confirmation paths.

### D-067 · Forecasts are a least-squares line over stored history, shown only when the fit is decent
The monitor already stores 15-minute rollups for 90 days, so forecasts need no new storage. The UI fits a straight line to the last 14 days of the fullest-filesystem % and memory % and projects when they reach 100 % and 95 %. It says nothing with less than two days or 24 points. Slopes under 0.05 points a day count as steady, and an r² under 0.5 is reported as "rising unevenly" instead of a date, because cache churn, log rotation and restarts make a confident date misleading. Disk uses the fullest mount because that's what history keeps; per-mount forecasts would need per-mount history. Linear is enough for "this disk fills in about six weeks". Seasonal models would be guessing on a homelab's irregular data.

### D-068 · GPUs come from `nvidia-smi` and amdgpu sysfs in the same metrics sample
The metrics script gains two sections. If `nvidia-smi` exists it runs one CSV query (under `timeout 3`), and for each `card*` with `gpu_busy_percent` it reads VRAM, the hwmon temperature and power. Both are cheap and need no extra tools. Missing values (`[N/A]`, passthrough VMs) become `None`. Intel's iGPU has no sysfs busy counter (it needs `intel_gpu_top` with root), so it's left out. History stores the busiest GPU's busy % in a new nullable `gpu` column (migration 0010), so old rows and hosts without GPUs stay NULL and the chart tab only appears when there's data.

### D-070 · Notes refuse secrets instead of encrypting them
Notes are plain markdown in SQLite and go into the encrypted backup like snippets. Rather than encrypting notes (which would need a key in the keychain and break search), saving refuses text that looks like it carries a secret: private key blocks, `name=value` / `name: value` where the name contains password, passwd, pass, secret, token, api key, access key, private key, credential or pwd, `scheme://user:password@`, and `Bearer` tokens (`core/src/redact.rs`). Placeholders (`••••`, `${VAR}`, `$VAR`, `<…>`, `****`) and short values pass. The rules are a subset of the UI's `redact()`, so **Mask them** always produces text that saves. "Send to terminal" uses the terminal's bracketed paste and never presses Enter, so a runbook can't run anything by itself (rule 5 still applies at the prompt).

### D-071 · History search is opt-in, unprivileged and leaves no copy
Shell history is where secrets leak most (`export TOKEN=…`, `mysql -p…`), so the HIST button only appears after turning on **Settings → Terminal → Shell history search**, and the backend checks the setting too. One script reads the last 5,000 lines of the login user's `~/.bash_history`, `$HISTFILE`/`~/.zsh_history`, `~/.zhistory` and fish's `fish_history` (no sudo, no other users). Parsing (bash `#timestamp` lines, zsh extended history, fish YAML) and filtering run locally; lines matching the secret rules of D-070 are dropped and only counted. Results are deduped (latest use wins), capped at 200 and live only in the open popover: they are not stored, logged or sent to DRIFT.

### D-069 · The security audit reads without root and only suggests fixes
The checks use what an ordinary login can see: `ss -tulnp` (or `netstat`), the sshd config files (first value wins, `Match` blocks skipped, drop-ins read first like the `Include` at the top of Debian's config), `systemctl is-active/is-enabled` for ufw, firewalld, nftables, fail2ban, CrowdSec, unattended-upgrades and dnf-automatic, `/etc/ufw/ufw.conf`, `/var/run/reboot-required`, `/etc/passwd` and `docker ps`. Asking for sudo on every audit (and for a bulk port map) would train people to type passwords without reading why, so anything that needs root (`ufw status`, `nft list ruleset`, `sshd -T`, other users' process names) is reported as unknown, never as a failure, and unknown checks don't lower the score. The score is 100 minus each failed check's weight and half of each warning's (root SSH login, extra uid 0 and exposed databases weigh most). Grades are A ≥ 90, B ≥ 75, C ≥ 60, D ≥ 40, F below. Fixes are text with commands in backticks and copy buttons; Nightgrid doesn't run them, because most of them (sshd, firewall) can lock the user out, and the text says how to avoid that. Reachability is judged from the bind address only (loopback, Tailscale's 100.64.0.0/10 and fd7a:115c:a1e0::/48, one address, every interface); the UI says a firewall can still block what's listed. Docker's published ports are taken from `docker ps` and replace their `docker-proxy` sockets, so a container shows by name.

### D-072 · Snapshots keep images in the database and files on the host
A stack snapshot stores, per service, the image reference, the image id and its repo digest in SQLite (migration 0012, deleted with the host, not part of backups because the ids only mean something on that host). Compose files and `.env` are copied on the host itself into `${XDG_STATE_HOME:-~/.local/state}/nightgrid/snapshots/<project>/<stamp>/` under `umask 077`, so `.env` secrets never leave the host and never reach Nightgrid's database (rule 1). The newest 10 per stack are kept on both sides. Rollback restores the files, re-tags each service's saved image id to its reference (pulling `repo@digest` first if the image was pruned; an image that was never pulled from a registry and was removed can't come back, and the run says so) and runs `docker compose up -d`, which recreates only what changed. A snapshot is taken automatically before Update and before Rollback, so every rollback is itself reversible. The confirmation names stack, host, files and services (rule 5).

### D-073 · Image update checks are anonymous, on demand and go only to the image's registry
Rule 7 allows registries for the update checker. Nightgrid asks the registry in the image reference (Docker Hub, GHCR, Quay, a self-hosted one) for the tag's manifest using the anonymous Bearer-token flow, picks the host's platform from an index, and compares the digest with the local image's repo digests. Nothing runs in the background, nothing is pulled, and registries that want credentials are shown as "needs login" (no registry passwords are stored). Versions come from the image's OCI labels (`org.opencontainers.image.version`/`revision`/`created`, label-schema, linuxserver's `build_version`). The changelog link is built from `org.opencontainers.image.source` only when it is an https GitHub URL: the compare page between the two versions or revisions, else the releases page. Links open in the system browser, never in the webview (rule 8). Redirects (registries hand blobs to a CDN) are followed only to https, and the Authorization header is dropped when the host changes.

### D-074 · The deploy wizard writes env values to `.env`, never to `compose.yaml`
The form generates `compose.yaml` with each variable as `${NAME}` and writes the values to the stack's `.env`, created with mode 600 before any content is written. The wizard masks values until **Show values**, and the review step shows `.env` masked. YAML scalars are quoted when they could be misread (leading special characters or digits, `: `, ` #`, booleans like `yes`/`on`). The backend refuses to overwrite an existing `compose.yaml` or `.env` unless the user confirms with a second button under a warning that names the files (rule 5), checks the result with `docker compose config -q`, and never starts the stack on its own: **Start it** is a separate click.

### D-075 · Backup jobs are read from what the host already shows, never from the repository
Reading a restic or borg repository needs its password, which would have to be stored or typed (rule 2), and opening a repository takes a lock that can collide with a running backup. So a job points at a systemd unit or a path. For a unit, one unprivileged script reads `systemctl show` (result, exit status, monotonic start and exit times turned into wall time from `/proc/uptime`, so it works on systemd versions without `--timestamp=unix`) and the last run's journal lines (by invocation id, else the unit's last 60 lines), where restic, borg `--stats`, rsync `--stats`/`-v` and rclone print totals. For a path, it reads the newest file three levels deep (restic and borg write new files on every backup) and `du -sk` (both under `timeout`). A job is stale when its last good run is older than its limit, a failed run with no good one since boot counts as stale, and a unit that hasn't run since the host booted only becomes stale once uptime passes the limit. Detection only suggests: timers whose ExecStart and cron lines that run restic, borg(matic), rsync or rclone, with a local repository or target taken from the command line where there is one; a command that looks like it holds a secret is shown as "hidden". Jobs are config and go into the encrypted export.

### D-076 · Proxy routes are parsed from config the proxy already has, read through the Docker API
Traefik routes come from router labels on running containers (`Host(...)` rules; HostRegexp is skipped), with the port from the service label. Caddy routes come from site blocks in the Caddyfile (`reverse_proxy` and `to` upstreams; global options, snippets and matchers skipped) and from caddy-docker-proxy labels. Nginx Proxy Manager routes come from its generated `proxy_host/*.conf` (`server_name`, `$forward_scheme`, `$server`, `$port`). Files inside containers are read with an exec of `cat` over the Docker API, so it works without the docker CLI or read access to volumes on the host. Each upstream is matched to a container by name or compose service, or by a published port when it points at the host. Certificates are read with `openssl s_client` run on the host against its own port 443 with SNI, which shows the certificate the proxy actually serves and makes no connection from this computer (rule 7). Domain names are checked before they reach the script. Traefik's file provider and `acme.json` (it holds private keys) and Caddy's JSON config are not read.

### D-077 · Log anomalies are opt-in and stay on this computer
Reading every container's logs and the journal every 10 minutes adds SSH traffic, so the rule is off by default and only uses connected hosts. Error lines (journal priority err and worse; container lines with error, fatal, panic, exception, traceback and similar) become patterns by folding tokens with digits, quoted values and leading timestamps, so the same error with different ids or durations counts once. The first read of a host learns from the last hour without alerting. After that a pattern never seen for that source fires a "new error" alert once, and a round with at least 20 lines and four times the average of the last 12 rounds is a burst. Patterns and the last 40 lines per source live in memory only; lines that look like they hold a secret are never kept or shown. **What broke?** sends the alert and those lines to DRIFT, the local model, after the usual preview; nothing goes to an external provider.

### D-078 · Profiles are the encrypted backup, with an in-app weekly reminder
The age-encrypted backup (D-057) already holds every config table, the settings and, when ticked, keychain secrets, and its format doesn't depend on the OS, so "profiles" is a name and a reminder rather than a new format. The backend records `lastProfileExport` on every successful export (file or sync folder) and clears the snooze; both stay machine-specific on import, like the sync folder. The reminder is an in-app card (not a desktop notification, which is for alerts), shown only once a host exists, after the chosen interval since the last export or, with no export yet, since this install first ran (kept in local storage). It never exports on its own: the passphrase is typed each time and never stored.

### D-079 · VM control uses the hypervisor's own CLI over SSH
libvirt and Proxmox both ship CLIs on the host (`virsh -c qemu:///system`, `qm`, `pct`), so one unprivileged script lists guests (plus `virsh dominfo` for vCPUs, memory and autostart) and no API tokens or extra ports are needed (rule 7). Proxmox's API would give more, but it needs a token stored in the keychain and HTTPS to port 8006 for what the CLI already shows. The list is read without root first; when a tool refuses (libvirt group, Proxmox needs root) the UI offers **Read as root** through the normal sudo prompt (rule 4). Guest ids are checked (digits for Proxmox, a conservative character set for libvirt names) and shell-quoted. Shut down, reboot and force stop are confirmed with the guest and host named, and force stop (`virsh destroy`, `qm stop`, `pct stop`) needs the guest's name typed, because it is the equivalent of pulling the plug (rule 5). Consoles run in a terminal tab; when they need root they run under `sudo` in the PTY, so sudo's own prompt asks there and nothing is put on a command line.

### D-080 · The phone status page is off by default, read-only and locked by a keychain token
A small HTTP/1.1 server in the app (tokio, no framework) answers `GET`/`HEAD /s/<token>` with one self-contained HTML page and nothing else: no API, no assets, no JavaScript, and a CSP of `default-src 'none'; style-src 'unsafe-inline'`. It never shows secrets, commands or (on the served page) host addresses. It binds to one address: this machine's LAN address (found by asking the OS which interface routes to TEST-NET-1, no packet sent), its Tailscale 100.64.0.0/10 address (routed via 100.100.100.100) or, only when picked, every interface with a warning. The 32-byte random token (ring's system RNG) lives in the OS keychain, is compared in constant time, is masked in the UI until revealed (rule 6) and can be rotated. Ten wrong tokens from one address lock it out for 10 minutes; at most 16 connections are served at once, each with a 10-second limit and an 8 KB request head. The setting is machine-specific: an imported profile never turns the server on. This is the user's own network, not telemetry: nothing is sent anywhere unless a device asks (rule 7).

### D-081 · The dashboard snapshot is the status page without refresh
The static export renders the same `render_html` with no meta refresh, so there is one renderer to keep safe (everything is HTML-escaped). It is written through a native save dialog on the Rust side (the webview gets no file system access, rule 8). Host addresses are off by default, because the file is meant to be attached or shared.

### D-082 · The network map discovers from one of your hosts, only when asked
Discovery runs one unprivileged `sh` script on a host the user picks, over the existing SSH connection, and only when **Scan** is clicked. It reads what the host already knows: its addresses and default route (`ip`, or `ifconfig`/`netstat` on BSD and macOS), the neighbour table (`ip neigh`, else `arp -an`), mDNS announcements (`avahi-browse -tpr`, with a timeout), Tailscale peers (`tailscale status --json`), Tailscale Funnel (`tailscale funnel status`), router port forwards over UPnP (`upnpc -l`, which asks the LAN's own router) and cloudflared ingress rules from its config file. The optional ping sweep sends one ping to each address of a private /24 or smaller subnet (fping when installed, else a bounded parallel `ping` loop); public ranges and anything larger than 254 addresses are refused. Missing tools become notes in words, not errors. Nothing contacts a service outside the user's network to test reachability (rule 7): "internet-facing" means the host has a public address, the router forwards to it, Funnel publishes it, or a tunnel serves it. Listening ports come from the existing security audit, also only on click. Unknown devices are offered as new hosts with the name and address filled in; nothing connects to them until the user does.

### D-083 · Notes are searched with the guide, unless hidden
DRIFT's retrieval indexes notes next to the bundled guide, rebuilt when a note's id, update time or hidden flag changes (so a save re-indexes it). Up to two matching notes go into the prompt in their own block, labelled as written by the user, and the reply lists the notes used as chips that open them. A per-note **Hide from DRIFT** flag (a new `hide_from_drift` column, default off) keeps a note out of the index entirely. Notes already refuse secrets on save, and the prompt still runs through the usual masking.

### D-084 · The custom scheme picks from curated swatches, not a colour wheel
A free colour picker makes it easy to end up with unreadable text or status colours that can't be told apart. The fourth scheme (CUSTOM, replacing PLAIN DARK) lets each palette slot pick from a short list: surfaces as a set of four (backgrounds and lines), text as a pair, and one list each for accent, info, active, danger, OK, warning and the neutral highlight. Tests check that every combination meets the same contrast rules as the built-in themes (text ≥ 4.5:1 on every background, status colours ≥ 3:1 on panels, dark text ≥ 4.5:1 on the accent). Each built-in scheme's values are in the lists, so **Start from** any scheme is exact. The choice is stored as token → `#RRGGBB` in `AppSettings.customTheme` (validated in Rust), so it is part of profile exports; values that aren't in the lists fall back to the default for that slot. Settings that still say `plain` show CUSTOM with effects off until another scheme is picked.

### D-085 · Terminal icon glyphs come from a bundled symbols-only Nerd Font
Shell prompts, MOTDs and tools like fastfetch use Nerd Font code points, which show as boxes unless a patched font is installed. Nightgrid bundles Nerd Fonts' *Symbols Only* (mono, v3.4.0, MIT) as one 1.2 MB woff2 under the name "NG Symbols", first in the terminal's font list but limited by `unicode-range` to the icon code points (the Private Use Areas and a few symbols), so text keeps JetBrains Mono and the font is only fetched from the app bundle when an icon appears. It is preloaded at startup, and terminals repaint (clearing the WebGL glyph atlas) when a font finishes loading, so a glyph drawn before the font arrived doesn't stay a box.

### D-086 · The PTY size is synced after open, and lost GPU contexts fall back to the DOM renderer
A terminal opens with its size at that moment, but SSH takes a moment to connect, and a split or sidebar toggle in between changed the size while there was no backend to tell, so the server kept the old width. The session now remembers the size it last sent and re-sends the current one when the backend opens and after every fit (fits are batched to one per animation frame). WebKit limits live WebGL contexts and can drop one when many panes are open, after sleep or when a pane is moved in the DOM; on context loss the WebGL addon is disposed so xterm falls back to its DOM renderer and every row is repainted. Panes repaint when they are re-parented by a split and when the window becomes visible again.

### D-087 · Key hints come from the shell on SSH and from the PTY locally
The app can't see which program runs inside an SSH shell, so the session-only hook ("edit in Nightgrid", now with options) also reports the command line: bash through a `DEBUG` trap armed by `PROMPT_COMMAND` (left alone if the user already has a DEBUG trap; the whole pipeline comes from `history 1`), zsh through `preexec`/`precmd`, fish through `fish_preexec`/`fish_postexec`. The line is cut to 160 characters of `[A-Za-z0-9 ._/+:=|-]` by the shell before it's printed as `OSC 7767 ; token ; line`, so it can't carry escapes, and only lines with the session's random token are read. An empty line means "back at the prompt". Local terminals need no hook: the backend asks the PTY for its foreground process group and reads that process's name with `ps`, only while the pane is on screen. The key maps are data in the UI (`keyhints.ts`); the strip and DRIFT's guide index read the same maps, and DRIFT is told what's running in the active pane. The strip has a fixed height so showing or hiding hints never resizes the terminal.

### D-088 · "This computer" can be a scan source
Discovery is one `sh` script (D-082), so it runs locally on macOS and Linux with `/bin/sh` and a 90-second limit, giving the same neighbour table, ping sweep, Tailscale, UPnP and tunnel results as a host. The script now avoids `timeout` where it doesn't exist and uses the right ping timeout flag on macOS and BSDs. Windows has no `sh`, so there the option explains that a host must be used.

### D-089 · Terminals use xterm's DOM renderer; panes keep their mount-time props
Blank panes after closing a split came from `TermPane`'s teardown reading its `session` prop, which already pointed at nothing once the closed pane's session was gone; the throw aborted Svelte's effect flush, so the surviving pane never mounted its terminal. Teardown now uses the session and element captured at mount. Separately, the WebGL renderer was dropped: WKWebView can clear or lose a WebGL canvas when a pane is re-parented (split, close, tab switch), it caps live contexts, and it cannot draw a transparent background. xterm's DOM renderer moves between parents without repainting tricks, supports `allowTransparency` (the background is `--bg-0` at zero alpha, so reverse video, drawn with the background made opaque, stays readable), and is fast enough for shell output. Cells are re-measured when a web font loads or a pane is re-attached (xterm only measures on a font option change, so the font stack alternates between two equivalent spellings), and fits wait two frames for the layout to settle.

### D-090 · Network device labels are keyed by MAC, fall back to IP
Devices that aren't hosts get a label (name, kind from a fixed list, up to 16 one-word tags, a note) in a `device_labels` table so a scan still says what each address is. The key is the lower-case MAC, which survives DHCP changes; a device seen without a MAC (ping only, Tailscale peers) is keyed `ip:<address>`. Labels are config, so they go into the profile export like bookmarks. DRIFT gets labels as plain lines in its context: all of them (up to 20) on the Network view, elsewhere only those whose name, tag or address appears in the question, to keep the small model's context short.


### D-091 · Built-in Tailscale is a tsnet sidecar behind a loopback SOCKS5 proxy
Tailscale's embeddable client (`tsnet`) is Go; linking it into the Rust app through `libtailscale` would mean cgo in every build and a C ABI to maintain. Instead a small Go program (`tailnet/`, about 20 MB) is bundled next to the app as a Tauri external binary and started only while **Built-in Tailscale** is on. It runs userspace networking (no TUN device, no admin rights, no system VPN) and offers the app one thing: a SOCKS5 proxy on `127.0.0.1`, random port, with a username and password made fresh each run, so other local programs can't use it. The app talks to it over JSON lines on stdin/stdout, and the sidecar exits when stdin closes, so it never outlives the app. Node state (machine and node keys) goes through an `ipn.StateStore` that keeps one AES-256-GCM file; the 32-byte key is generated by the app and stored in the OS keychain (rule 1). It is built with `ts_omit_logtail` and also disables log upload at runtime, so nothing goes to `log.tailscale.com`. With the client on, the app contacts the Tailscale control server (or the configured Headscale) and DERP relays, which is the integration the user turned on (rule 7). All TCP dials go through `tailnet::dial`: 100.64/10 and `fd7a:115c:a1e0::/48` addresses and MagicDNS names go through the proxy; addresses inside accepted subnet routes and bare peer names try a direct connection for 2.5 s first, then the proxy, so the same host works on the LAN and away; everything else, and everything while the client is off, dials directly (so a running system Tailscale keeps working).

### D-092 · A per-host tailnet address is a dial-time fallback, not a second host
A host can have a `tailnet_address` (migration 0016). The dialer keeps a table of main address → fallback, refreshed whenever the host list loads or changes, and tries the address that worked last first (for at most 3 s), then the other one, remembering which answered. Because this happens below SSH, the SSH target and host-key check stay on the main address, so a host reached on its 100.x address isn't a "changed host key" (rule 3), and service checks on the same address get the fallback too.

### D-094 · Planned power states come from three sources and never alert
An unreachable host is only an outage if nobody meant it. The core keeps an in-memory note per host (`power::note`): set by Nightgrid's own power actions just before the command runs (the connection usually drops before an answer), by systemd-logind's `PrepareForSleep`/`PrepareForShutdown` signals, which a small unprivileged watcher (`gdbus monitor --system`, else `dbus-monitor`) follows over the host's pooled monitoring connection while it is up, and, without any note, by an optional per-host sleep window in local time (migration 0017). When a sample fails, the metrics poller reports `Suspended`, `Rebooting`, `ShuttingDown` or `Asleep` instead of `Offline`, with the reason as the message; the offline alert only looks at `Offline`, so nothing fires. Notes clear on the next good sample (a resume signal clears too); `Rebooting` expires after 15 minutes. Notes aren't stored: after a restart of Nightgrid an unreachable suspended host is offline again unless its sleep window covers it. Power actions use the same sudo path, logging and typed-name confirmation as the existing reboot (rules 4 and 5).

### D-095 · Wake-on-LAN from here or from a relay host
The magic packet (6 × `ff`, then the MAC 16 times) is a UDP broadcast, so it only reaches the sleeping host's LAN. From this computer it goes to 255.255.255.255 on ports 9 and 7. Each host can name another saved host as its relay (`wake_relay_id`); the app then runs `wakeonlan`, or a Python one-liner, on the relay over SSH, which works away from home (for example through the built-in tailnet). The relay id is remapped on profile import like other host references.

### D-096 · Network discovery: containers out, vendors bundled, quiet devices found
Neighbours on container bridges (`docker0`, `podman0`, `cni0`, `br-*`, `veth*`, `cali*`) are containers the Docker view already shows, so devices inside those IPv4 subnets are dropped and counted in a note. Vendors come from a bundled, offline copy of the IEEE MA-L registry (`core/data/oui.tsv`, about 1 MB, built by `scripts/gen_oui.py` from the BSD-licensed `oui-data` package); locally administered MACs are labelled "Random MAC" instead of guessed (rule 7: no lookup service). IPv6 neighbours with the MAC of an IPv4 neighbour fold into it (`also`). The default route is read from all tables and IPv6, preferring IPv4; a link-local IPv6 gateway is resolved to the IPv4 device with the same MAC. Devices that never answer ping are still found when the host mounts a share from them (`/proc/mounts` or `mount`: NFS, SMB), has an established TCP connection to them on one of its own LAN subnets (`ss -tn`), or, during an opt-in sweep, accepts or refuses a connection on one of a few common ports (`nc -z`, else bash `/dev/tcp`), which also fills the neighbour table.

### D-097 · SSH key manager: files and agent in, authorized_keys over the existing connection
Keys are what the user already has: every `*.pub` in `~/.ssh` that parses (certificates skipped), joined by SHA-256 fingerprint with the agent's identities, so agent-only keys (1Password, Secretive, Pageant) show up as well. New keys are ed25519 only, made with the `ssh-key` crate russh already uses (no new crates beyond `getrandom`/`rand_core`, which were already in the lock file, for the OS RNG). They are written with `create_new` at 0600 / 0644 into `~/.ssh` (made 0700 if missing), and an optional passphrase encrypts the file in OpenSSH's own format and is then dropped. It isn't put in the keychain, because remembering belongs to a host's connection (rule 2) and the existing passphrase prompt already offers that. Host changes are plain shell over the pooled connection, so they work on any host with `sh` and need no agent forwarding: adding greps for the key's `type base64` and appends only when it's missing, creating `~/.ssh` and the file with the right modes. Removing rewrites the file in place (`grep -v` into a temp file in `~/.ssh`, then `cat` back), so owner, mode and SELinux labels stay. The comment is stripped of quotes and backslashes and the key blob is checked to be base64 before either reaches a command line. "Which key works where" reads `authorized_keys` rather than trying every key against every host, which would mean one login per key and host, failed-login noise and possible fail2ban bans. Rotation runs in the UI one host at a time: push the new key, open a separate connection that authenticates only with the new key file (same jump hosts), optionally switch the saved host to that file, and only then remove the old key. A failure stops that host with the old key still in place. Removing a key (alone or as part of a rotation) is destructive (rule 5): the single removal names the host and key and needs the host name typed, and a rotation lists every host and needs the old key's name typed, which works for any set of hosts. `~/.ssh/config` is never touched.

### D-098 · Power schedules are systemd timers on the host; group power never prompts per host
A schedule that lives in Nightgrid only runs while the app is open, which is exactly when nobody needs a 23:00 shutdown. So a schedule is a `oneshot` service plus a timer in `/etc/systemd/system` on the host (`Persistent=false`, so a missed shutdown doesn't fire at the next boot), written as root through the usual sudo path (rule 4). Wake-ups can't run on a sleeping machine, so they go on the host's **Wake from** relay as `nightgrid-wake-<mac>`, sending the same packet as the WAKE button (D-095). The unit text travels base64-encoded inside a single-quoted `printf`, so nothing in it reaches the shell; the `ExecStart` line is checked to hold no `%`, `$` or backslashes, which systemd would expand. Each unit's first line is `# nightgrid {json spec}`, so listing reads the specs back from the host and Nightgrid stores nothing locally. There is one unit per action (one per MAC for wake-ups); saving again replaces it, and only units named `nightgrid-power-*` / `nightgrid-wake-*` can be removed. A scheduled shutdown or suspend is announced by systemd-logind like any other, so the watcher from D-094 shows it as planned. Group power runs the existing per-host power command one host at a time after the group's name is typed (rule 5's multi-host rule). It doesn't prompt for sudo per host, because a row of password prompts would be easy to click through: hosts that need a password that isn't remembered are reported as skipped.

### D-099 · The incident timeline is recorded events plus what the host remembers, merged on read
Most of a host's history already exists on the host: the journal knows its boots, failed units and OOM kills, the package managers log their transactions, and Docker keeps recent container events. Copying all of that into the local database would duplicate it and go stale, so the timeline reads it when the tab opens with one read-only script (no sudo, nothing installed; sections the login can't read come back empty and say why) plus Docker's events API over the existing connection. What only Nightgrid knows is recorded as it happens in a new `host_events` table (migration 0018): alerts firing and clearing (from the alert loop, so it covers everything the tracker sees), power actions and wake-ups, compose runs with their outcome, deploys, rollbacks, container and unit actions, package upgrades and automation runs. Rows hold a kind, a level, a title and a short detail; any text that looks like a secret is replaced before it is written (rule 1), and rows are kept 90 days and at most 5000 per host. It is history, not config, so it stays out of profile exports and goes away with its host. A `die` followed by a `start` of the same container within two minutes is shown as one "restarted" entry. Package dates from apt and dnf are converted on the host (`date -d`), so its own time zone and DST apply. DRIFT's summary uses the existing Explain path with the filtered entries as text, newest 150 at most.

### D-100 · Expiry watch keeps names and dates, reads certificate files over SSH, and looks domains up only on a click
Things that expire are scattered: service certificates (already checked by the service checker), proxy certificates (M10g), certificate files that no HTTP endpoint serves (an internal CA, a mail server, a VPN), domain registrations and API tokens. One board shows them all, soonest first. Service and proxy certificates are joined in the UI from data that is already there, not copied. Everything else is a `watch_items` row (migration 0019): a kind, a name, an optional host, a target (a path or a domain), the date, warning days and a note. A token's value is never stored, only its name and end date, and names or notes that look like secrets are refused (rule 1). Certificate files are read with `openssl x509 -enddate` over the pooled connection, all files of a host in one command, when added, on request and every 12 hours from the alert loop for hosts that are connected anyway; a read error is shown and keeps the last known date. Domain expiry has no local source, and asking a registry is an outside call, so it never runs in the background: **Look up** runs `whois` on a host the user picks, at that moment (rule 7 stays about this computer, and the click is explicit). Otherwise the date is typed in. The alert (`ExpirySoon`, "EXPIRING") is warn inside the item's window and critical in the last three days, and shares the existing certificate switch so there is one place to turn expiry alerts off. Items are config and travel in profile exports; a certificate item goes with its host.

### D-101 · Config drift compares checksum manifests; the baseline and its file copies stay on the host
"What changed on this box" needs a before picture. Keeping copies of `/etc` in the local database would put secrets there (rule 1), so a baseline is saved on the host itself, in `~/.nightgrid/baselines/default` with mode 700: a manifest (SHA-256 of every readable file under `/etc` up to 1 MB, plus compose files in the host's saved stack folders, plus the package list from dpkg, rpm, pacman or apk) and a `tar.gz` of the same files, `.env` files left out. It is written to a new folder and swapped in, so a failed save leaves the old baseline. A comparison reads the live manifest the same way (one script, no sudo: unreadable files like `/etc/shadow` are skipped, which keeps root-only secrets out of it entirely) and compares by checksum, so nothing but hashes and package versions crosses the connection until the user opens one file. Then both versions are fetched (capped at 512 KB, from the archive for the baseline side) and diffed in Rust with Myers' algorithm, three lines of context, giving up past 2000 edits; nothing is stored. `.env` files are compared by checksum only and never fetched. Host-to-host comparisons hide a short list of files that are meant to differ (hostname, machine-id, hosts, SSH host keys, netplan/interfaces, NetworkManager connections, WireGuard and Tailscale state), behind a switch. Lines shown in a diff go through the same secret masking as the rest of the UI, with click to reveal (rule 6).

### D-102 · The update center is one view over the existing per-host commands, and batches never prompt
Checking and upgrading many hosts is the per-host Updates tab run in a loop, so the Fleet view adds no backend commands. It calls `system_updates` and `system_upgrade_run` for each host, three at a time, so a dozen hosts neither queue one by one nor open a dozen SSH sessions at once. Results stay in memory: package lists go stale within hours, and opening the view re-checks after 30 minutes. A batch upgrade passes no sudo password. Hosts that are root, have NOPASSWD or have a password remembered in the keychain run, and the others are listed as skipped instead of prompting, for the same reason as group power (D-098). Rule 5 asks for a typed confirmation that names the targets. A selection can be any set of hosts, so the phrase is the host's name for one host, the group's name when the selection is exactly one whole group, and otherwise `upgrade N hosts`. The dialog lists every host with its package count. Nothing reboots automatically; a flagged host's **Reboot…** goes through the existing single-host confirmation. Image updates reuse the per-stack registry check (rule 7: registries, only on a click) and link to the stack instead of pulling, so the M10f snapshot-before-update path stays the only way images change. rpm-ostree hosts are handled as one "system image" row. `rpm-ostree upgrade --check` gives the new version, `status --json` gives the booted one, and a first deployment that isn't booted means an image is staged and a reboot is pending. Upgrading runs `rpm-ostree upgrade`, which stages the image and leaves the running system alone. A check that polkit refuses over SSH shows its error as a note rather than a false "up to date".

### D-103 · Pools are read without root; the forecast is a two-week straight line on local hourly points
Pool health has to be cheap enough to check in the background, so it uses only sources an ordinary login can read: `zpool status` (allowed for any user), `/proc/mdstat`, and btrfs's sysfs files (`devinfo/<id>/missing` and `error_stats`, kernel 5.14+), plus `/proc/mounts` for a btrfs filesystem mounted `degraded`. `btrfs device stats` and `btrfs scrub status` need root, so btrfs scrub state isn't shown. A missing device, a pool that isn't ONLINE, a degraded array or data errors are critical, and error counters on an otherwise healthy pool are warnings. A mirror or raidz vdev marked DEGRADED isn't reported on its own because the device under it already is. The background check runs every 30 minutes on hosts that are already connected, like the backup check, and opens no connection of its own. A forecast needs history, and the minute metrics hold a single disk percentage, so usage per mount is kept in its own table (migration 0020): one row per host, mount and hour, written by the metrics poller at most every ten minutes and kept 90 days. That is about 2,200 rows per mount. It is history, not config, so it stays out of exports and goes away with the host. The rate is a least-squares line over the last 14 days. A short window follows a log that started growing yesterday, and a fit over many points shrugs off a single cleanup. It needs at least a day and six points, and growth under 0.01 % of the size per day counts as flat. "Size" is used plus available, matching the disk-full alert, so root-reserved blocks don't make a disk look emptier than it is. The alert ignores mounts with no point in the last day, because a host that isn't watched shouldn't keep a stale forecast alive, and it clears only after three hours below the threshold, since a forecast moves as usage moves. Nothing is projected with curves or seasonality: a line is easy to explain, and the sparkline shows what it is based on.

### D-104 · A test restore runs on the host as root, in the backup unit's own environment
A backup you have never restored from is a hope, not a backup. Proving it can be read back needs the repository password, which Nightgrid must not hold (rule 1). The unit that runs the backup already has it, through `EnvironmentFile=`, `Environment=` and sometimes `User=`. So the test is one root script on the host (through the usual sudo path, rule 4). It reads those settings with `systemctl show`, sources the environment files there, switches to the unit's user with `runuser`, and runs the tool with stdin closed, so nothing can prompt. The password never crosses the connection and is never on a command line. The script restores one random regular file under 20 MB from the latest snapshot (restic `ls --json`, borg `list`) into a fresh `mktemp -d` folder under `/tmp` and compares its size with the listing. A trap deletes the folder on any exit, and restic runs with `--no-lock --no-cache`, so the repository and live files are untouched. A path job for a folder copy (rsync and similar) copies a random file out and compares SHA-256 checksums. A path job for a restic or borg repository has no password source, so it says to test the unit job instead. rclone remotes aren't supported yet. It is not destructive, so a plain confirmation is enough (no typed name), and it only runs on a click, never in the background, because it reads real data and can take minutes. It gives up after 20 minutes. Only the outcome is stored with the job (time, pass or fail, and the restored path or the error, with anything secret-looking hidden), so the board can show "restore tested 3 days ago". The board itself moved to Fleet, since it always covered every host; System keeps its per-host tabs.

### D-131 · Proxmox firewall: the API as is, and one rollback session for host-level changes
The Proxmox firewall already has the right shape: datacenter, node and guest levels, ordered rules, security groups, aliases and IP sets, in files under `/etc/pve` that `pve-firewall` recompiles by itself. Nightgrid edits it only through `pvesh` with each list's digest, and it validates rule fields on both sides, so a value can never become a second option. Guest-level changes can't block the node, so they apply directly. Datacenter, node and group changes can block the node, for example by turning the firewall on while Nightgrid reaches the node over a tailnet, which Proxmox's built-in management exception (local network only) doesn't cover. So they run under a rollback like the network apply (D-130), with one difference. Firewall work is usually several small edits, and a timer per edit would restore only the last step. So the first host-level change saves `cluster.fw` and the node's `host.fw` (or notes that they're absent) under a session token. Later changes reuse that token, keep the first copy and only restart the timer. **Keep** ends the session, and the rollback returns to the state before the first change. If a change fails while it is the first of its session, the files are restored at once and nothing stays armed. IP set entries, log options and conntrack settings stay in the web UI. They are rarely touched, and the rule editor already accepts IP sets by name.

### D-130 · Node network: Proxmox's staging, plus a rollback the node runs by itself
Proxmox already separates editing from applying. API changes go to `/etc/network/interfaces.new`, and `ifreload` makes them live only on request. Nightgrid keeps that model and shows the staged file as a diff before anything happens. Staging, reverting and removing are harmless until applied, so they need no confirmation, except removing an interface, which names it. Applying is the step that can lock you out: a wrong address or a bridge without its port can cut off the node and the SSH connection Nightgrid uses to fix it. So apply uses the same pattern as the host firewall (D-118). It saves the live file on the node, arms a systemd timer (or a detached sleep) that restores it and reloads, and then runs Proxmox's own apply. If the apply call itself fails, the old file is restored at once. Otherwise the view shows a 90-second countdown with **Keep**. If Nightgrid can still reach the node to press Keep, the node is reachable, so there is no separate connectivity probe. If it can't, nothing needs to arrive: the node rolls back by itself. Editing is limited to the node Nightgrid is connected to, because the rollback has to run where the change happens. Other nodes can be added as hosts. Only Linux bridges (`vmbrN`), bonds and VLANs are offered. OVS and SDN zones stay in the web UI for now, since they are less common and work differently.

### D-129 · Hardware edits: a short list of keys, the digest, and Proxmox's own pending model
The config API accepts any key, including `args` (raw QEMU arguments) and `hookscript`, which run arbitrary commands as root on the node. Nightgrid passes only a fixed list of keys: CPU, memory, disks, NICs, PCI/USB passthrough, boot and start options, tags and notes. The values are shell-quoted, single-line (notes may have newlines) and length-capped, so a value can never become a second option. Anything outside the list stays a web UI or shell job on purpose. Every change carries the digest the config was read at, so an edit made elsewhere in the meantime makes Proxmox refuse instead of silently overwriting. Nightgrid doesn't track hot-plug rules itself. It reads `/pending` and shows what Proxmox says waits for a restart, so the answer is always Proxmox's own. Rule 5 is scaled by what can be lost. Detaching a disk, removing a NIC, a drive or a passthrough device asks and names it. Deleting an unused disk erases data, so its key must be typed. Growing a disk, adding things and changing values don't ask, because they destroy nothing, and Proxmox can't shrink a disk anyway. Edits keep the parts of a value the form doesn't show (a NIC's MAC and queues, a disk's options), so a VLAN change doesn't silently renumber a MAC that a DHCP reservation depends on. Passthrough warns about IOMMU group mates, because those devices leave the node too, and about IOMMU being off. Checking firmware settings is left to the user, since Nightgrid can only see the symptom.

### D-128 · Creating guests: few choices, sensible defaults, keys instead of passwords
Proxmox's create wizards have dozens of fields, and most homelab guests use the same answers. Nightgrid asks only for what differs between guests (id, name, size, storage, ISO or template, bridge and VLAN) and fixes the rest to the web UI's recommended choices: VirtIO SCSI single with discard and IO thread, VirtIO network, `x86-64-v2-AES` CPU and the guest agent. UEFI adds OVMF, q35 and an EFI disk, and Windows 11 always gets UEFI plus a TPM, because it won't install otherwise. Anything else is a later hardware edit (part 4), not a wizard step. A container needs SSH public keys and never gets a root password. A password would have to cross the command line of `pvesh` (rule 4 forbids that for sudo, and the same reasoning applies) or be stored somewhere (rule 1). Keys are public, so they can be passed as they are. Unprivileged with nesting is the default, as in current Proxmox. Clone, convert to template and destroy are the documented API calls. A linked clone is offered only from a template, because Proxmox refuses it otherwise. Destroy is the most damaging step in the view, so it needs the guest's name typed (rule 5) and is offered only for stopped guests. It purges the guest from jobs and HA and removes unreferenced disks, but leaves backups on backup storages alone. Downloads run on the node with `download-url` and `aplinfo`, so the node fetches the file and nothing passes through this computer (rule 7: the only outside traffic is the node's own, to an address you typed or to Proxmox's catalogue). A SHA-256 you paste is checked by Proxmox, which deletes the file on a mismatch.

### D-127 · Proxmox snapshots and backups: Proxmox's own tools, confirmations scaled to the damage
Part 2 adds no new mechanism. Snapshots, vzdump, restore and the backup job list are the same `pvesh` paths the web UI calls, so retention, pruning, protection, verification and Proxmox Backup Server storages keep working as Proxmox defines them. Nightgrid only lists, starts and follows. The backup list reads every storage with backup content from the node it belongs to. A shared storage answers on every node, so files are de-duplicated by volume id. Freshness thresholds are fixed and simple: red when a guest has no backup or the newest is over 7 days old, orange over 2 days. A guest no job covers is called out separately, because "not scheduled" is the usual cause of "no backup". Confirmations follow rule 5 and scale with the damage. Rolling back, deleting a snapshot and deleting a backup name the guest, node and snapshot or file. Restoring over an existing guest replaces its disks, so it also needs the guest's id typed. Restoring as a new guest picks the next free id and needs no confirmation, because it destroys nothing. Deletion uses `pvesm free <volid>`, which takes the volume id as is. Protection uses the content API with the volume id's `/` encoded as one path segment. That encoding is the one detail not yet checked against a real node, and it fails visibly if wrong.

### D-126 · Proxmox goes through pvesh over SSH, not the HTTPS API with a token
Proxmox's web UI and API (port 8006) need either a password login or an API token. Nightgrid would have to store that token, which rule 1 allows only in the keychain, and keep port 8006 reachable from this computer. `pvesh` is the same API, served locally on the node to root. So Nightgrid runs it over the SSH connection it already has, through the usual sudo path (rule 4, the same prompt as System). There is no new secret, no new port and no TLS certificate to trust, and every path, parameter and permission is the documented API, so later parts (snapshots, backups, create and clone, hardware, networking, firewall) are more `pvesh` calls rather than new mechanisms. One batched script reads `/version`, `/cluster/status`, `/cluster/resources`, `/cluster/tasks` and the local node's status in a single round trip. Each answer is parsed on its own, so one failing read becomes a note and the rest still shows. Any node of a cluster answers for the whole cluster. Screens and consoles still need the guest's own node, because `qm vncproxy` and `qm terminal` run there, so the view says which node to add for guests elsewhere. Actions return a task id (UPID): Nightgrid follows that task's status and log until it ends, then rereads the cluster, the same way the web UI shows progress. Shutdown, reboot, pause and force stop need a confirmation that names the guest and node (rule 5). Start and resume don't. Nothing from Proxmox is stored locally. Development had no Proxmox host, so parsing is tested against fixtures copied from the API's documented shapes and against a fake `pvesh` run by a real shell. The first run on a real node may still need small fixes.

### D-125 · Command widgets are read-only by rule, stored in the database, and only poll while shown
A tile that shows any command's output is the most open-ended widget possible, which is the point (keep features open ended), but it also runs on a timer with nobody watching. So a command is checked with the same destructive-action heuristic the automation runner uses (`automation::danger`), on save and again before every run, and anything it flags is refused outright rather than confirmed: rule 5 asks for a confirmation naming the target each time, which a refreshing tile can't give. sudo, su, doas and pkexec are refused too, because rule 4 means sudo would prompt every time, and an unattended prompt is a hang. The command runs as the SSH user over the pooled connection with a 30 s limit; the output kept for display is capped at 4 KB and only in memory. Definitions live in their own table (migration 0032) rather than in the dashboard layout, because the layout is settings JSON shared by presets: the layout only holds a `cmd:<id>` kind, so the same widget can sit on several dashboards, and backups and profiles carry the table with its host id remapped. The parse rules are deliberately few (first number, regex group, line count, exit code, first line) with thresholds in either direction; anything fancier belongs in the command itself (`awk`, `jq`). Timers are reference counted per widget and run only while a tile is on screen and the window is visible, so a dashboard full of tiles costs nothing when you're elsewhere.

### D-124 · Network tests use iperf3 on the hosts, with a server that stops itself
Measuring a link needs traffic between the two hosts themselves; anything run from this computer would measure its own Wi-Fi or tailnet path instead. So Nightgrid starts an iperf3 server on the target and the client on the source, both over their existing SSH connections, and only between hosts you added (rule 7: no outside speed-test service). iperf3 is the one outside tool: it is packaged everywhere and the numbers are comparable with what people already know, which a home-grown TCP blaster wouldn't be. The server is started as a daemon on port 5201 with a pid file and a detached watchdog that kills it after two minutes, and Nightgrid stops it explicitly as soon as the client is done, so a lost connection never leaves a listener behind. Each run measures both directions (`-R` for the second) and records what the receiver got, plus ping's average, spread and loss. Results are kept (200 per pair) so a link can be compared with itself: about 100 Mbit/s flags a link that may have negotiated Fast Ethernet, and a run under 70 % of the pair's median is called out. The address the source connects to defaults to the target's saved hostname and can be changed, because the address Nightgrid uses (often a tailnet name) isn't always the one the hosts use between themselves.

### D-123 · GPU history keeps one number per host per measure, like the CPU columns
Collection already read every GPU (nvidia-smi, amdgpu sysfs) since M10c, but history kept only the busiest GPU's busy %. Three columns join it in `metric_points` (migration 0030): the fullest VRAM in %, the hottest GPU in °C and the power of all GPUs added up in W. They follow the existing pattern of one aggregate per host rather than a row per GPU, so the minute, 15-minute and hourly tiers, pruning and zoomed ranges work unchanged and multi-GPU hosts still show the one that matters (fullest, hottest, total draw). Points from before the migration keep NULL and charts simply start where data starts; the hourly tier isn't backfilled for them. The insert now builds its parameters from the column list, so adding a column is one place. The Overview gets a GPUS widget listing every GPU's live numbers from the samples already in memory, so it adds no polling.

### D-122 · Stacks from git: git runs on the host with the host's credentials, and a deploy is a reset to one reviewed commit
The compose files have to end up on the host anyway, so the repository is cloned there and every git command runs there over SSH; nothing is cloned to this computer and no git library is added. Authentication is the host's own (a deploy key in `~/.ssh`, or a credential helper), with `GIT_TERMINAL_PROMPT=0` and SSH `BatchMode=yes` so a missing key fails with a message instead of hanging; common failures (publickey, unknown host key, login needed, missing branch) get a hint. Storing a token in the keychain and feeding it to git on stdin was left out: it would put a second credential path in the app for something a deploy key already does, and rule 7 is satisfied either way since only the host talks to the git server. Checking fetches only the tracked branch into `refs/remotes/origin/<branch>` and lists commits and file stats limited to the stack's folder, so one repository can hold several stacks (one tracked row per folder). Deploying takes a specific commit id the user reviewed (never "whatever origin has now"), checks that it is on the branch or behind HEAD, refuses while tracked files have local changes, saves an M10f snapshot, then `git reset --keep <commit>`; the same command rolls back to the previous deploy, whose id is kept with the row. The stack is then brought up with the normal compose run, so output, cancel and the timeline work as they do for Up. The checkout's stack folder is added to the folders scanned for stacks, so it appears in the list before it has containers. Removing a git stack only stops tracking it; deleting files on a host is left to the user.

### D-121 · The .env vault encrypts values with an age key from the keychain; the host's file is only written on deploy
Rule 1 forbids plaintext secrets in SQLite, but the keychain is a poor store for dozens of small values per stack (no listing, slow on some platforms, a prompt per item on macOS). So each value is encrypted with age to an x25519 key that lives in the keychain (`vault-key/<id>` plus a `current` pointer), and the table (`env_vars`, migration 0028) holds only base64 ciphertext, the key id, the name, a masked flag and the order. The key id travels with each row, so a profile import brings rows and their key together: the key is one of the opted-in secrets in an encrypted profile export, and import adopts it as an extra key without replacing this computer's current one. Rows whose key isn't present are shown as LOCKED instead of failing the list, and a deploy is refused while any are. Values cross IPC only on an explicit Reveal (masked ones) or for plain variables when the vault opens (rule 6), and the add form uses a password field for masked values. Deploying reads the host's current `.env` and shows a diff by name only (added, changed, removed, unchanged), never values, warns that names missing from the vault are dropped, saves an M10f stack snapshot first (so Snapshots can put the old file back), writes with umask 077 and mode 600, and records a timeline entry. It doesn't restart anything: the result offers **Up** separately, because recreating containers is a different action from writing a file. Quoting follows compose's `.env` rules (bare when safe, single quotes, else double quotes with escapes and `$$`). Importing reads the host's `.env` into the vault with its values replacing the vault's for the same names; masked starts from a name heuristic (`PASSWORD`, `TOKEN`, `KEY` and so on) or the existing row's flag.

### D-120 · Pi-hole and AdGuard Home are integrations that talk to their own APIs
Both DNS filters already have HTTP APIs for everything the dashboard needs, so they are integrations (a URL plus a password in the keychain, rules 1 and 2), not host scripts: no SSH or sudo is needed, they work for a Pi-hole on a router or an appliance Nightgrid can't log in to, and the calls go only to the configured URL (rule 7). Pi-hole means version 6 and its REST API (`/api/*`); the v5 `api.php` with a token in the query string isn't supported. A Pi-hole session (`POST /api/auth`, then `X-FTL-SID`) is opened for each read or change and closed with `DELETE /api/auth` straight after, because Pi-hole allows only a few sessions at a time and a 30-second poll would otherwise use them up; an app password works the same as the web password. AdGuard Home uses HTTP basic auth on `/control/*`. Both are mapped to one status (queries, blocked share, clients, top blocked domains, lists with entry counts and last download, local records) and one set of typed changes (blocking on, paused for a time or off; add, remove, enable or disable a block or allow list; download the lists again; add or remove a local record), each validated before it is sent: list URLs are http or https only, record names are host names (AdGuard also takes `*.` wildcards and a name as the answer, Pi-hole an IP address only). A Pi-hole list change uses `PUT`, which replaces the list's settings, so its current groups are read first and sent back unchanged. Turning blocking off and removing a list or record are confirmed with the target named (rule 5); pauses use the servers' own timers, so blocking comes back even if Nightgrid is closed.

### D-119 · Caddy sites are edited in the Caddyfile and checked by Caddy; Traefik routes go to a file Nightgrid owns
Caddy's Caddyfile is the user's file, often with snippets, imports and comments, so it is edited as text and only in ways that leave the rest byte for byte: a new site is appended, a site's block is removed by its line range, and an upstream is changed only in a site with exactly one one-line `reverse_proxy` without matchers; anything else is edited as text in the app, with the same checks. Every change is shown as a diff first (secrets masked until revealed, rule 6). The write is one script where Caddy runs (over SSH with sudo for a Caddy on the host, through a Docker exec for a Caddy container): the old file is copied to `.nightgrid-backups/` next to it (the newest 10), the new text, base64-encoded, goes to a temporary file in the same directory (so relative imports resolve), `caddy validate` checks it, the Caddyfile is overwritten in place rather than renamed (a bind mount of a single file keeps pointing at the same inode), and `caddy reload` loads it (`systemctl reload caddy` as a fallback on the host); if the reload fails, the copy is written back and reloaded. The file read is identified by a SHA-256 prefix and re-read before writing, as with crontabs (D-117), so a change made elsewhere isn't overwritten. Caddy's JSON config and caddy-docker-proxy labels stay read-only. Traefik has no validate command and its routes usually live in container labels, which belong to compose files (changing them means recreating containers), so the editor writes only `nightgrid.yml` in the file provider's directory, generated from typed routes (names, domains, upstream URL, entry points, TLS and resolver all validated) with the routes as JSON on its first line so it reads back exactly; Traefik watches the directory and picks it up without a restart. A file of that name that Nightgrid didn't write, a single-file provider or no file provider block the editor with the reason and the flag to add, rather than editing Traefik's static configuration. Logs name the change, never the file's text (rule 1).

### D-118 · Firewall changes arm a rollback on the host before they apply
A firewall change can cut the connection that would undo it, so the safety net has to live on the host, not in the app. Every change is one root script: it copies the current rules (`/etc/ufw` and `/etc/default/ufw`, or `/etc/firewalld`) to `/var/lib/nightgrid/fw-rollback/<time>` (the newest 5 kept), writes a restore script there, arms it with `systemd-run --on-active` as the transient `nightgrid-fw-rollback` timer (or a detached `sleep` with a pid file where systemd isn't running), and only then applies the change; a change that fails restores the copy at once. The app then opens a fresh SSH connection through the same route (jump hosts included) to show that a new login still works, and offers Keep, which stops the timer, or Undo now; if nothing answers, because the app was closed or the host is unreachable, the host restores the rules by itself when the timer runs out (30 s to 15 min, 2 min by default). Only one change can be pending per host. Changes are typed (`FwChange`), validated field by field and shell-quoted, never free text; ufw and firewalld are edited with their own commands (`ufw allow|limit|deny|reject`, `ufw delete <rule>`, `firewall-cmd --permanent` then `--reload`), while plain nftables and iptables are shown read-only, because editing a raw ruleset safely would need a parser and Nightgrid doesn't own those rules. A change that could close the SSH port Nightgrid uses for that host (deleting or denying the rule that covers it while nothing else allows it, turning ufw on without an allow for it, setting incoming to deny or reject without one, removing firewalld's `ssh` service or a port range holding it) is named in the confirmation and needs the host name typed (rule 5), on top of the rollback. Snapshots stay on the host (rule 1); the app keeps only the pending change's summary and deadline in memory.

### D-117 · Crontabs are edited as whole files with a hash check; timers are Nightgrid's own units
`crontab -e` can't be driven over SSH, and editing a crontab line by line on the host would need a parser in shell. So the crontab is read (`crontab -l`, with `-u user` as root for others), the change (add, update, remove, turn off or on) is applied in Rust to that text, every job is checked (schedule parsed, one line, no unescaped `%`), and the whole text goes back through `crontab -`, which validates it again. The text read is identified by a SHA-256 prefix and re-read just before the write: if it changed (someone ran `crontab -e`, another Nightgrid window), the write is refused instead of overwriting their change. The new text travels base64-encoded inside single quotes so no command in it is ever interpreted by the outer shell, and the old crontab is copied to `~/.nightgrid/cron-backups` on the host first (copies stay on the host, as with config baselines; the last 20 are kept). Turning a job off comments it with a fixed `#nightgrid-off ` prefix, so it can be turned back on exactly and ordinary comments are never mistaken for jobs. Logs name only the kind of change, never the command, which may carry a token (rule 1). `/etc/crontab` and `/etc/cron.d` stay read-only: they belong to packages. New timers are a `nightgrid-job-<name>` service and timer pair with the spec as JSON in a comment on the first line, the same pattern as power schedules (D-098), so only units Nightgrid made can be edited or removed; other timers get enable, disable and run now through the existing unit actions. `ExecStart` doubles `%` and `$` so systemd doesn't expand them and hands the command to `/bin/sh -c` unchanged, and the schedule is checked with `systemd-analyze calendar` on the host before anything is written, so a typo fails with systemd's own message rather than leaving a dead timer.

### D-116 · The access audit is read on demand with one script; nothing is kept
An access audit answers "who can get in and who tried", which changes slowly and matters when someone looks, so it is read when asked for rather than collected in the background: one POSIX `sh` script per host (journal or auth log for sshd's `Accepted`, `Failed` and `Invalid user` lines over 7 days, `last`, `fail2ban-client`, `cscli decisions list -o json`, sudoers, each shell user's `authorized_keys`, `sshd -T` or the config files), sectioned output parsed in the core crate with tests. Most of it needs root, but prompting for every host in "Audit all" would be easy to click through, so root is used only when it needs no prompt (root login, NOPASSWD, a password the user chose to remember, rule 4) and the report lists what it couldn't see, with "Read as root…" asking once for that host. Nothing is written to the host or stored here: the reports live in the UI's memory, so user lists, addresses and keys don't end up in the database or profile exports. Failed attempts are counted once each (`Invalid user` and `Failed … for <valid user>`, not the `Failed … for invalid user` that repeats the first), grouped by address. Auth log timestamps use the host's own clock and UTC offset (printed by the script), with the year taken from the host's date and a line in the future treated as last year. Public-key logins carry the key's fingerprint, matched in the UI against the user's own keys so the report says which of their keys was used, linking it to the key manager (M10k). Posture checks such as the firewall and listening ports stay in System → SECURITY; the findings here are about access only.

### D-115 · Log search runs where the logs are; saved searches alert from the alerts loop
Nightgrid doesn't collect logs: shipping every host's journal and container output to this computer would mean an agent or a log store, and most of it would never be read. A search instead runs at the moment it's asked for, over the connections Nightgrid already has: `journalctl --since @t -o short-unix` over SSH and the Docker connection's log API, all hosts in parallel with a 90 s limit each, so one slow or offline host is reported next to the results instead of holding them back. Plain case-insensitive text is narrowed on the host with `grep -i -F` (shell-quoted; unit names are validated against a unit-name pattern before they reach the command line), so a quiet search over a busy journal moves only the matching lines; regular expressions and case-sensitive text are matched here with the `regex` crate, which has size limits and no backtracking, so a pattern can't hang the app. Each host returns at most the newest 20,000 journal lines and 5000 lines per container (60 containers), and the merged stream keeps the newest 2000. Lines that look like secrets are replaced before they leave the backend (rule 1 and 6), using the history-search filter. Saved searches are rows with the query as JSON; their alerts run inside the alerts loop every 5 minutes, only on hosts that are already connected (an alert check never connects to anything), each over the lines since that search's last check, and they report their own scope so a search that is turned off or deleted clears its alerts. A host id inside a saved query isn't remapped on profile import: such a search falls back to the hosts that still match, and searching all hosts is unaffected.

### D-114 · A third rollup tier instead of a downsampling job; reports from the uptime tables
Long ranges get an hourly tier in the same `metric_points` table, filled by the same running-average upsert as the 15-minute tier, so there is still no batch job and a crash loses nothing. Each range is served from the coarsest tier that still gives a useful number of points (1-minute up to 2 days, 15-minute up to a month, hourly beyond, about 8,760 points for a year), and zooming simply asks for a shorter span, which picks a finer tier when it is stored. A migration seeds the hourly tier from the 15-minute rows already kept, weighted by sample counts, so a year view isn't empty on day one. Uptime reports are computed from `uptime_hours` and `outages` for whole local calendar months (start and end at local midnight, computed with the OS time zone), so they agree with the bars; outages are clipped to the month, and a subject with nothing recorded is "no data", not 0% or 100%. The export is one HTML page with inline CSS (screen, light and print styles), no scripts and no external loads, like the status page; printing to PDF is left to the browser, which avoids a PDF dependency.

### D-113 · Uptime is what Nightgrid saw, in hourly buckets plus outage rows
Uptime comes from the signals the app already has: the metrics poller's state per host (the same one that drives "host offline") and the service checker's latest result, sampled on every alerts round whether alerts are on or not. Each round adds the seconds since the previous one (capped at 60 s, so a closed lid or a stopped app is a gap, not uptime) to an hourly row per host or service, in separate up, down and asleep columns. Availability is up / (up + down): time nobody watched is unknown and planned sleep (suspended, sleep window, rebooting or shutting down from Nightgrid) is neither, so a host that sleeps every night can still be at 100%. Hour rows make any day boundary possible later (days are grouped at the viewer's local midnight in SQL) and stay small (about 9,000 rows per subject per year); a separate outage row per down spell, extended each round and closed when the subject is seen up, asleep or not reported, gives exact starts, lengths and the first error for the outage list and later the SLA reports. Rows have no foreign key because a subject is a host or a service, so the six-hourly prune also drops rows whose host or service is gone. Like the incident timeline, this is history, not configuration: kept 400 days locally and left out of profile exports.

### D-112 · UPS shutdown runs in the app's alerts loop, through the hosts' own sudo
NUT already does reliable UPS-driven shutdown (`upsmon`) where it is set up, and Nightgrid doesn't replace it: it reads `upsc` over the SSH connection it already has, so the UPS's state shows next to the rest of the fleet and turns into ordinary alerts (folded under the host like any other host alert), and the optional group shutdown covers hosts that `upsmon` doesn't. Nothing is installed on hosts (only `upsc`, which is checked for first) and no NUT port is opened to this computer. Readings happen in the existing alerts loop, only for hosts that are already connected, so watching a UPS never wakes or connects to anything by itself. The countdown lives in the backend, not the UI, so it works with the window closed; a generation counter makes cancel, power-back and a removed watch all race-free (the waiting task only acts if nothing changed since it started). Shutting a group down is destructive across hosts (rule 5), so arming it means typing the group name, the countdown is announced in a notification that ignores quiet hours and as a banner on every view with Cancel, and a cancelled shutdown stays off for the rest of that outage. The shutdown itself uses the same power command as the System view, with sudo through stdin and a remembered keychain password only if the user chose one (rule 4); hosts that would need a typed password are reported as failed rather than prompted for, since nobody may be there to type it. The UPS's own host goes last so the reading host stays up while the others go down.

### D-111 · Runbooks are notes with a scope, matched in the UI
Notes already had what a runbook needs (markdown, code blocks typed into a terminal without Enter, host link, export, DRIFT search), so a runbook is a note with three more columns: a runbook flag, the alert kinds it's for and an optional service (with the existing host). It matches an alert when every part that is set fits, and an unscoped runbook matches nothing so one forgotten checkbox can't put a note on every alert. Matching is a small pure function in both Rust (tested, for later use from the backend) and TypeScript (where the alerts list and notes already are), with the same tests. Step lists use `- [ ]` and `[label](view:id)` in the markdown renderer only when it renders notes, so DRIFT's replies can't produce links; ticks are kept for that reading only, because a runbook is a template and storing ticks would mean editing the note every time it is followed. Links go to views (validated against the view list), not to arbitrary actions, so a note can't trigger anything; automation playbooks stay in Automation, reachable with `view:automation`.

### D-110 · Dependencies fold alerts at delivery time; the tracker stays as it was
Folding happens after the tracker, on the active and pending alerts each round, not by suppressing conditions: every alert still exists, has its own history and timeline entry, and stays visible in the list under its cause, so turning folding off or removing a dependency changes nothing but presentation and notifications. Edges are stored in their own table with foreign keys to hosts and services (cascade on delete, remapped on profile import like the other tables) rather than in the settings, because they point at row ids. Two edges are implicit and not stored: a service checked on a host depends on that host, and any alert about a host depends on the host being up; the user's edges add the rest. The cause is the furthest-up node that is down, so a chain folds under its root rather than nesting. Loops are refused when added, and the walk is loop-safe anyway because the implicit edges can close one. Because a service check fires after 90 s and "host offline" after 120 s, a downstream alert whose cause is still pending is held for up to five minutes instead of notifying, then dropped if the cause fires or sent if it doesn't. Folded alerts that were never notified don't send a "resolved" message either.

### D-109 · Tours are data that watch the page; they never act
A tour is a list of steps, each naming a `data-guide` target (the same ids DRIFT's pointing already uses, so a test catches a tour that points at nothing) and what ends it: a click on that control, a view becoming current, a selector appearing or disappearing, or Next. The store only listens, with a capture-phase click listener and a 200 ms poll, so it keeps working while views re-render and needs no hooks in the views it visits; it never clicks, types or switches views, which keeps the user in control and means a tour can't do anything the user didn't. Steps whose control isn't on screen say so and can be skipped instead of blocking. The callout is a `popover="manual"` element so it sits in the top layer above modal dialogs (re-raised when a new dialog opens), and it lets every click through except its own buttons. Tours don't use the model: they are written by hand and tested, available even with DRIFT off; the model can only offer one by id (`[[tour id]]`), validated against the list like its other actions. "What can I do here?" lists the guide targets of the current view that are actually on screen, also without the model. The first-run offer is a settings flag (`tourOffered`), so it shows once per install and travels with profiles.

### D-108 · Commands from DRIFT go to a prompt, never to Enter; summaries use only what the app already has
A drafted command is useful only if it is easy to try, but a 4B model can be wrong, so the TERMINAL button pastes it at a prompt (the host the question was about, or the focused shell) and stops there; the user reads it and presses Enter. Only one-line commands get the button, because pasting several lines into a shell runs all but the last. If the command check finds a DANGER pattern the button needs a second click that says so. The daily summary deliberately starts no SSH work: it reads alerts, monitoring, services and whatever update, disk and backup checks already ran, and says plainly when something wasn't checked, so asking for a summary is instant and doesn't wake sleeping hosts. Alert triage uses a fixed table of causes and first checks per alert kind (exact, reviewable) and lets the model tailor it to the alert's details. The deeper history search runs on the host's history files already read for the recent lines, picks lines with the question's words (not host names or filler words), and keeps the same secret filter as history search.

### D-107 · DRIFT's skills are exact checks computed in the app; the model explains them
A 4B model is good at explaining and bad at spotting: it misses the `-v` in `compose down -v`, invents a vulnerability in a fine compose file, or gets cron arithmetic wrong. So the skills that need precision are plain code with tests (risky command patterns, compose findings, an error table, cron parsing and next runs), and the model gets their results as facts in a CHECKS block with an instruction not to contradict or drop a DANGER item. The same results are drawn above the reply, so the user sees the exact findings even when the answer around them is weak. Which checks run is decided from the question and the attached text (a backticked command, a one-line selection that looks like a command, a `services:` file, error-looking text, a cron expression or schedule words), not by the model choosing tools, which a small model does unreliably. The compose reader handles only the YAML subset compose files use rather than adding a YAML dependency; anything it can't read gives a clear "couldn't read" instead of guesses. The error table is the seed of the offline reference the knowledge base (M11) extends. Nothing here runs commands or reaches the network.

### D-106 · Dashboard layouts are placed in the UI and only validated in Rust, stored with the settings
Placement (pushing widgets out of the way, closing gaps, clamping sizes) is interactive and runs on every pointer move, so it lives in a small set of pure TypeScript functions with tests instead of a grid library (no new frontend dependencies) or a round trip to Rust. The core crate checks what gets saved: known widget kinds, ids of letters, digits and dashes, widgets inside the 12 columns, no overlaps, and limits of 12 dashboards, 48 widgets each and 24 presets. Layouts are part of `AppSettings` rather than their own table, because they are preferences: they then travel in profile exports and restore with no extra code. A layout from a newer version with a widget kind this version doesn't know is drawn as a placeholder; and because one broken layout must not cost the user their other settings, `AppSettings::load` retries without the dashboards when only they fail to validate. "Per-workspace layouts" became named dashboards shown as tabs, since Nightgrid has no separate workspace concept to hang them on. Widgets for checks that run over SSH (updates, disks, backups) show the last result and a button, so opening the Overview never starts work on the hosts.

### D-105 · VM desktops use a VNC client built into the app, carried over the host's SSH connection
The plan was to embed noVNC, but that means vendoring a large JavaScript library and running a WebSocket bridge, and the frontend has no dependencies outside its build (rule 8: no remote content, a strict CSP). The RFB protocol is small, so the client is written in Rust in the core crate: version 3.3 to 3.8, no-auth and VNC-password security (DES from the `des` crate, already in the lock file through russh), and the encodings QEMU serves well: Raw, CopyRect, ZRLE (zlib through `flate2`, also already present) and DesktopSize. Nightgrid asks for 32-bit pixels with red in the low byte, so ZRLE's 3-byte pixels and Raw rows copy straight into an RGBA buffer. Tight and the cursor pseudo-encoding were left out; ZRLE keeps the stream small enough over SSH. The bytes never touch a socket on this computer: a libvirt display found with `virsh domdisplay` is reached with a `direct-tcpip` channel to its loopback port (or `direct-streamlocal` for a socket), and a Proxmox VM through `qm vncproxy` on an exec channel. That command refuses to run without `LC_PVE_TICKET`, which it sets as the VM's VNC password for 30 seconds, so Nightgrid makes up a random one per session, sends it on stdin after sudo's password line (never on a command line, rule 4) and answers the VNC challenge with it. A libvirt VNC password is read only when the host shows it with `--include-password` and is kept in memory for the handshake. Pixels are decoded in Rust and the UI long-polls for patches of changed rectangles as raw bytes, which arrive in the webview as an ArrayBuffer without JSON or base64. Long polling gives natural back-pressure: a slow canvas just asks less often while the decoder keeps the newest picture. Input is keysyms from `KeyboardEvent.key` (so the host's layout decides the character), with releases matched to their presses by physical key and everything released when the screen loses focus. RDP stays with the system client, which already does it well: a tunnel on 127.0.0.1 with a free port through the host, and a `.rdp` file that holds only that address, opened with the opener plugin from Rust (the webview's opener scope stays limited to http(s) links). Tunnels live in memory and end with the app. Embedding an RDP client was left for later.

### D-092a · Public names that resolve to tailnet addresses are routed through the built-in tailnet
Routing by the host string alone (D-091) sends a public name such as `app.example.com` straight to the OS stack, even when its DNS record points at a 100.x tailnet node; without a system Tailscale nothing answers. While the built-in client runs, `dial` now resolves a name that isn't an IP literal and isn't already routed (at most 1.5 s, within the caller's timeout). If every address is a tailnet address, it connects through the sidecar's SOCKS proxy to the resolved address (IPv4 first), not the name, because the sidecar's resolver may not see the same public records. Names with a mix of tailnet and other addresses stay direct for now, since the public address may be the one meant to work, and a failed or empty lookup dials directly as before. Callers keep the name for TLS SNI, the Host header and SSH host keys; only the TCP stream changes. With the built-in client off there is no extra lookup, so a system Tailscale keeps working as before.

### D-093 · DRIFT gets the user's own hosts as facts, and history only per host

### D-135 · Tailscale SSH through "none" auth, and browser-style dialing
Roben's Tailscale SSH host hung on LINKING. Tailscale SSH doesn't check keys. It accepts the "none" method when the tailnet policy allows the user, and in **check** mode it first sends a banner with a login URL, then holds the answer until the URL is approved. Nightgrid went straight to the agent's keys, never showed the banner and had no limit on the wait. Now every hop asks with "none" first, as OpenSSH does: other servers just answer with their method list, so nothing changes for them. Banners and keyboard-interactive instructions go to an `on_notice` sink. The app keeps the latest one per host while the host connects, and the UI polls it (`ssh_auth_notices`) to show **Approve in browser**. Polling a small map was simpler than adding the first app-wide event channel. Each step is bounded by `auth_wait` (5 min), and so is the whole login. A refusal from a server that identified as Tailscale gets a message about the policy instead of "no agent identity was accepted". A separate "Tailscale SSH" auth method would have needed a table rebuild for the column's CHECK constraint. It wasn't needed either, since agent auth now covers it, so the host editor only hints at it for tailnet addresses.
Services showed public sites as "timed out connecting" while a browser loaded them. `TcpStream::connect` tries a name's addresses one after another, and on a network that drops IPv6 the first (IPv6) attempt eats the whole check timeout. `tailnet::direct` now does Happy Eyeballs (RFC 8305): it interleaves the families and starts the next address 250 ms after the previous one, and the first connection wins. That fixes it for every connection, not only checks. The proxied sites that answered 502 in about 3 s look like real upstream failures at the reverse proxy (Plex and Portainer through the same proxy were fine). Failures now carry the answering server, the address dialled and the start of the error page, so the board shows where it broke instead of only "502".

### D-137 · Log alerts judge events by level, remember patterns, and need repetition
Two harmless lines on Roben's server became NEW ERROR alerts. A Stirling-PDF WARN line matched because "Exception" was in the logger's class name. A convertx 404 trace was split into two "new" errors. The old rules matched words anywhere in a line, kept known patterns only in memory (relearned from the last hour at every start), and alerted on a single line. Now `logwatch` groups lines into events (continuation lines join their head within 2 s), takes a declared level first (`level=`, JSON `level`, an upper-case or bracketed level word among the first words, a leading `error:`), and only uses wording when there is no level. Journal lines keep their priority filter. 404/NOT_FOUND events are counted separately and only alert as a spike against the source's own history. Fingerprints are a SHA-256 prefix of the blanked pattern, stored per host and source (`log_patterns`, migration 0034). Hashes rather than text, because a pattern can still hold something sensitive (rule 1). A pattern is new for 24 h after its first sighting. Within that it alerts only at the repeat threshold, unless the event is fatal or the container is unhealthy or restarting. Restart grace uses Docker's log timestamps against the container's start time, worked out from its status line, so no extra inspect per container. A restart of any reverse-proxy image on the host counts for every container there, because restarting the proxy re-tests every site. Each new pattern gets its own alert key with its fingerprint, which is what **Mute pattern** stores. Mutes live in the alert settings (fingerprint or regex, per source), with a label only when it doesn't look secret. Notes and muted/404 counts are in the alerts snapshot (memory only, notes kept 24 h), so nothing is dropped silently. Container state alerts are untouched and stay immediate.
Triage for log alerts no longer gets the generic causes table. `log_classify` runs the same event rules over the attached lines. The UI adds `docker inspect` facts and a verdict (harmless, problem or unclear) and lists only commands that run as written. The system prompt gains grounding rules. A small model will still paraphrase, but now from facts that say "running, healthy, likely harmless".
Diagnostics export is a plain text file assembled in Rust, not a zip, so it can be read before it's shared. Settings carry no secrets (those are in the keychain). Log lines are passed through the same secret detector as notes and history, and a matching line is replaced whole.

### D-139 · Three DRIFT model sizes, picked by memory
Roben asked for reasonable model options and help choosing. The catalog (`helper::model::MODELS`) holds three, each pinned to a repository commit and its SHA-256 as D-063 did for the first: Qwen3 4B Instruct 2507 (Light), Qwen3 8B (Balanced) and Qwen3 30B-A3B Instruct 2507 (Best), all Q4_K_M from unsloth's GGUF repos, all Apache-2.0. No newer 8–14B instruct-only Qwen GGUF existed, so Balanced is the hybrid Qwen3 8B: DRIFT appends Qwen's `/no_think` switch to the system message and a streaming filter (`helper::think`) drops any `<think>` block, so replies look the same as the others. The 30B-A3B model is a mixture of experts with 3B parameters active per token, so it costs memory, not speed, which makes it the right "best" for big-memory machines rather than a dense 14B or 32B. Nothing bigger is offered (Roben: "nothing way overkill").
Fit is about memory. Each model's need is its file plus a measured-by-shape context allowance (8k tokens). On Apple Silicon the budget is what Metal can wire (two thirds of RAM, three quarters above 36 GB) less 1 GB; on CPU builds it is half of RAM for "fits" and 70% for "tight", since the model shares RAM with everything else. The recommendation is the largest comfortable fit. Detection runs once per app run, locally, with tools the OS has (`sysctl`, `/proc`, PowerShell CIM, `nvidia-smi`); a GPU on Windows or Linux is shown but not used, because those builds run llama.cpp on the CPU (D-063), and the card says so. The chosen model is a setting (`helper_model`), so the switch happens on the next question: the engine notices the id changed, frees the old model and loads the new one. Downloads are per model and leave the setting alone until done, so DRIFT keeps working on the old one; "Download and use" switches when the checksum passes.

### D-140 · Device identity and inventory from the scanning host, routed ranges by hand
Roben approved a deeper network scan with the constraint that nothing outside the machines already in play is needed (no outside service, no extra installs). Each source is optional and a missing tool is a note, not an error. Lease entries only name devices the scan actually saw, so a stale lease never invents a device. The type guess (`netident::guess_kind`) is an ordered list of strong signals (UPnP device type, mDNS service, names people give devices, maker, Tailscale OS, open ports) mapped to the existing label kinds, so the guess and the user's label speak the same vocabulary and the label always wins.
The inventory (`net_devices`, migration 0035) uses the device-label key (MAC, else `ip:`), so a device keeps its history across address changes and scanners. It stores no secrets and nothing beyond what the map already shows. "Missing" is only computed inside ranges this scan swept, so scanning from another network never marks the first one's devices as gone. Trusted is a flag on the inventory row rather than a label tag, so trusting a device doesn't create a label. The newest 5000 devices are kept.
Scanning beyond the router: a scan runs from any host (or this computer), so a host at another site or on another VLAN scans its own network fully. ### D-141 · Topology map: inferred tree, hand-set parents and an expected picture, laid out in the UI
Roben asked for a map that draws real connections (a smart lamp to the access point it's on), remembers how the network is supposed to look, and is more than four columns. ### D-142 · Network tools run on the chosen machine with its own commands

### D-151 · DRIFT's read-only server checks: named kinds, fixed commands, per-host opt-in
Roben asked for DRIFT to see as much as possible of what's going on on a server, read only. ### D-145 · Security findings and the network watch
Findings come from two places. What a discovery already holds (UPnP forwards, public interface addresses, DHCP server identifiers from dhclient, systemd-networkd, NetworkManager or `ipconfig getpacket`) is checked by fixed rules in `core/src/netsec.rs` (`discovery_findings`) and returned in `Discovery.findings`, so it costs nothing extra. The web check is a separate click because it connects to devices: one python3 script from the scanning machine opens each of 12 web ports with a short timeout, keeps the peer certificate (parsed in Rust with x509-parser for expiry and self-signed) or the first page (title, `Server:`, `WWW-Authenticate`, a password field), and matches a short list of admin-page signatures of gear known for default passwords. It never submits anything. The watch reuses discovery on a schedule rather than a separate agent: settings `netWatch` (scanner host or this computer, minutes, sweep, three alert switches), run in its own task from the alerts loop so a 30-second sweep never delays other alerts, merged into the inventory like a manual scan. "New" means untrusted and first seen in the last 24 h (not just "new to this scan"), so the alert stays until the device is trusted or a day passes; "missing" only counts expected-map devices in a subnet the scan covered, so a scanner that can't see a VLAN doesn't report everything there as gone. A failed scan keeps the previous conditions. Results live in memory; nothing new is stored beyond the inventory.

### D-144 · Wiring hints from the scanner: LLDP, traceroute to routed ranges, Tailscale paths
Where a device physically connects can't be seen from the IP layer, so the map uses what the scanning host can tell for free. LLDP: `lldpctl -f keyvalue` (lldpd) or `networkctl lldp`, when present, name the switch and port the scanner is plugged into; the switch becomes a node between the router and the scanner (an existing device when its management address or MAC matches, otherwise a node of its own), skipped when the neighbour is the router itself. Routed ranges: one `traceroute -n -m 6 -q 1 -w 1` (or tracepath) per swept range to its first address; the last hop outside the range becomes the router those devices hang under. Both only add inferred parents, so a parent the user set by hand still wins (D-141). Layout inference now prefers the most specific link the scan saw (a switch or router) over the main router and the tailnet. Tailscale: `CurAddr` set means a direct path, otherwise the peer's home relay region; the UI says that idle peers show as relayed. SNMP bridge tables and access-point client lists need credentials or vendor APIs, so they wait for an integration the user configures.

### D-147 · Web UIs in their own window, with no IPC
Roben asked to open a Docker service's web GUI (AMP and the like) inside the app when the connection works. The main window keeps its strict CSP and never loads remote content (rule 8), so an iframe is out; each web UI gets its own `WebviewWindow` with `WebviewUrl::External`. That window has no capability (the only capability file names `main`), Tauri already refuses app commands from remote origins without a remote capability, and the invoke handler now also rejects any webview whose label isn't `main`, so a page can't reach a command even if one of those layers changes. Navigation is limited to http(s) (plus about/blob/data), and pop-ups go to the system browser rather than becoming more windows. The window's web engine can't use the built-in tailnet, so reachability is tested with a plain OS socket (1.5 s); when that fails, or the URL is loopback as the host sees it, the existing temporary tunnel (`tunnel_open_temporary`) forwards it, with the host's own name mapped to `127.0.0.1` on the host. Before a window opens, one `GET` checks that something answers and that HTTPS is trusted: the web engine can't be told to accept a self-signed certificate per site without a platform-specific hook, so instead of a blank window the user gets a note and **Open in browser**, where they can choose to proceed. Which ports look like a web UI is a pure function in core (`webui::targets`, a skip list of non-web ports and a ranking of common web ports) with a `nightgrid.webui` label to override; the targets ride along on `ContainerView`, so no extra calls. Windows are keyed by URL so a second click focuses the first. Cookies live in the app's webview store, so logins persist like a browser profile; nothing is written to Nightgrid's database.

### D-150 · DRIFT's prompt fits the model's window
The first question in a fresh conversation failed with "9432 of 8192 tokens" once the views and the Library grew. Two causes: the system prompt listed every "point" target (244, about 6–7k tokens on its own), and `chunkMarkdown` only split at blank lines, so long bullet lists in the user guide became single 4–7k character "chunks". Now the system prompt always lists the sidebar rows, view tabs and controls visible everywhere, plus at most 24 view-specific targets picked for the question (its words, the current view, views it names and the views of the retrieved sections). Blocks over 900 characters are split at top-level list items or lines, with code fences closed and table headers repeated. `fitTurns` (helper/prompt.ts) budgets the whole conversation against the loaded model's window, estimating 3 characters per token (on the safe side for Qwen's tokenizer) and keeping 768 tokens for the reply: sections are capped at 1800 characters, CHECKS and each MY HOSTS block at 3000, then it drops the lowest-ranked sections (round robin across guide, Library and notes, so the best of each stays), older question/answer pairs, the remaining sections, half the selection and half the live facts, in that order. What it left out shows in "What I was given". The backend's `Engine::fit` is a safety net with the real tokenizer: it drops older turns, then cuts the middle out of the newest message (keeping its start and the question), and fails only when the system prompt alone doesn't fit. The window itself is sized per model at load (`hardware::context_for`): 16k or 12k when the bigger f16 cache (`ModelSpec.kv_per_token`) still fits the comfortable memory budget with 1 GB to spare, otherwise 8k; CPU builds stay at 8k because reading long prompts there is slow. The loaded window is reported in `HelperStatus.context` and the webview budgets with it (8k until a model is loaded).

### D-152 · An error reference DRIFT matches exactly, kept as Library articles
Roben asked for a reference of about a thousand Linux server errors, mainly for DRIFT. It lives as plain Markdown on a new Library shelf (`docs/kb/errors`, 20 areas, 1,124 entries) so people can read and search it like any article and it is indexed by the same retrieval. Each entry is `### <the literal message>` with `Means:` and `Fix:` lines, so `chunkMarkdown` makes one small chunk per error. Retrieval alone ranks by words and would miss a pasted log line among many similar ones, so `ui/src/lib/kb/errorref.ts` also matches exactly: each heading becomes a case- and quote-insensitive pattern where `<placeholders>` match any short run of text, an entry needs at least 12 literal characters to count, the longest literal match wins and substring duplicates are dropped. Up to three hits from the question and the attached text go into the existing CHECKS block (480 characters each, inside its 3,000-character cap from D-150), so the model gets the right entry without it costing the Library sections their place. Everything is bundled and offline; the catalog lines are generated by `scripts/kb_errcat.py` and a test keeps them in step.
### D-160 · The journal: one table of changes, written where changes happen
Roben approved a homelab journal: "what did I change, where, when", searchable, and readable by DRIFT. It is a new table (`journal`, migration 0038) rather than more rows in `host_events`, because the two answer different questions: the timeline is what *happened* on one host (alerts, boots, OOM kills, read from the host) for 90 days; the journal is what the user *changed*, fleet-wide, for two years (50 000 rows), including entries with no host (integrations, hand-written notes). Every timeline event Nightgrid itself caused is also journaled (`journal_cmd::from_timeline`, area from the event kind, Proxmox by title), so existing hooks feed it for free; the editors that had no timeline entry (files, cron, timers, firewall, Caddy, Traefik, `.env` vault, SSH keys, baselines, integrations) call `journal_cmd::record` directly. Text edits store a compact unified diff from `confdiff::line_diff` (2 lines of context, cut at 32 KB); each line goes through `redact::line_has_secret` and is replaced when it looks like a secret, and `.env` vault entries carry names only (rule 1). Saving a file on a host reads its old text first for the diff; local files aren't journaled. Recorded entries can't be edited or deleted one by one (only the whole journal can be cleared), so it stays an honest record; hand-written ones can. The host's name is stored with each entry so the record survives removing the host. DRIFT gets at most 12 entries per mentioned host (25 fleet-wide for "what changed" questions) from the last 14 days, as one line each with diff sizes but not diff text, to stay inside the prompt budget (D-150). Off in Settings → Features means nothing is recorded. The journal is history, not configuration: it isn't in profile exports.

### D-161 · Blueprints: an encrypted bundle and a plan of additive steps
Roben approved blueprints for disaster recovery and moving to a new server. A blueprint holds only what can be put back without guessing: stacks (compose files, plus `.env` or the vault's values for it), the login user's crontab, Nightgrid's timers, the firewall's rules, a Caddyfile and Nightgrid's Traefik routes. Packages, users and arbitrary `/etc` files are left out: rebuilding those blindly across distributions breaks more than it fixes, and config drift (D-118) already compares them. The file is the same kind of age passphrase file as a profile (`core/src/blueprint.rs`, format `nightgrid-blueprint`), so nothing is written unencrypted (rule 1) and no new dependency is needed; values are zeroized on drop and the captured and opened blueprints live in memory only until saved or closed. Rebuilding never runs a script: the target is read first, `plan` turns each piece into a step (new, same, differs, manual), and only ticked steps run, each through the existing editors' code paths (`cron_merge`, `timer_job_save`, `caddy_save` with its validate-and-restore, `traefik_save`, the vault's `import_env`), so their checks and journal entries apply. Everything is additive: crontab lines are merged (settings first, jobs appended), Traefik routes are added by name, and existing files are overwritten only when the user ticks a "differs" step. Firewall steps only add allow and limit rules (they can't lock anyone out); deny rules, default policies and turning a firewall on are marked manual so they go through System → FIREWALL and its rollback (rule 5). Stacks keep their source paths; moving them elsewhere is a later addition if it turns out to be needed.

### D-162 · Sandbox clones: isolated by config, marked by tags, expired by the node
Roben approved sandbox clones: a copy of a guest to test an update on, then keep or discard. The copy is a normal Proxmox clone (full, or linked from a template; from a snapshot when picked), then `isolate` rewrites its configuration before anything can start it: every NIC gets `link_down=1` (or moves to one chosen bridge without its VLAN tag), PCI/USB passthrough is removed (two guests can't hold one device), a container's bind mounts of node folders are removed (they're shared with the source, so a sandbox would write real data; storage-backed mount points are copied by the clone and stay), and `onboot=0`. Isolation by config was chosen over a Proxmox firewall rule set because it needs no datacenter firewall turned on and survives the firewall being off. All state lives on Proxmox as tags (`nightgrid-sandbox`, `ng-sbx-of-<vmid>`, `ng-sbx-until-<unix>`), so nothing is stored locally (rule 1) and another Nightgrid sees the same sandboxes. Expiry is a transient `systemd-run` timer on the node so it fires while the app is closed; it re-reads the guest's config and destroys only when both the sandbox tag and the exact `until` tag it was armed for are still there, so a reused id, an extended sandbox or a kept one is never touched by a stale timer. A node restart drops a transient timer; the tab shows the sandbox as overdue rather than Nightgrid destroying anything on its own. Destroy, keep and extend refuse guests without the tag. Built and tested against the Proxmox fixtures until a Proxmox host exists.

### D-163 · Power & cost: profiles × CPU history, checked against the UPS
Roben approved a power and cost view. Hosts have no portable way to report wall power: RAPL covers only the CPU package and is root-only on current kernels, and smart plugs would need an outside integration per brand. So each host gets a profile (watts at idle and at full CPU, typed in or from a preset), and the draw is the line between them at the hourly CPU average, plus measured GPU watts above their own minimum (the GPU's idle is part of the profile). That is honest to within the profile's accuracy, and a UPS that reports `ups.realpower` (or load × its rating) is shown next to the summed estimates of its group as a check. Everything is computed from data already kept (the hourly metric tier and the UPS loop's last reading), so the tab adds no polling and nothing runs while it's closed. Idle windows use local time (the UI sends its UTC offset), need 5+ days per hour of day and 85% of those days idle, and only windows of 3+ hours are offered; the hint points to the existing scheduled power (D-098) instead of acting on its own. Price and currency are settings; profiles are a small table keyed by host (deleted with it).

### D-164 · Library quests: fixed read-only probes named in the article
Roben approved the Library as a quest tracker. A step becomes checkable by ending its line with `{check: id}`; the id names a probe in `core/src/quest.rs`, never a command, so an article (or a future user-added one) can't make Nightgrid run arbitrary shell. Parameterised probes (`container:`, `service:`, `port:`, `command:`) take only validated names and are quoted. Every probe reads without sudo: anything only root can read (an sshd drop-in, ufw state on some distros) comes back as "couldn't tell" with the reason rather than prompting for a password, because a guide check must never change or escalate anything. sshd settings are read the way sshd does (Include expansion, first value wins, stop at Match) since `sshd -T` needs root. One script runs all of an article's checks in one SSH exec (at most 40). Results are shown and can tick the guide's boxes, but aren't stored: they describe one moment on one host, and ticks remain the user's own record on this computer. A core test fails if any article names an unknown check.
